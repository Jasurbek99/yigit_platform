# Truck Board / рейсы Planning — ручная проверка

Фича слита в `main` через PR #24 (2026-09-30). Документ описывает, как проверить её руками: подготовка, 16 сценариев с ожидаемым результатом, что делать после проверки.
Описание фичи — `docs/obsidian/processes/truck-board.md`.

Весь прогон занимает около 1–1,5 часа. **Проверяй в режиме mock:** рейсы берутся из файла, данные Planning и реальные рейсы никто не трогает. Режим live нужен только для короткой проверки в конце, раздел 5.

---

## 1. Подготовка (один раз)

1. **Обнови код.** В основном дереве должен быть `main` с коммитом `1eb33b65 Merge pull request #24`.
   Перед `git pull` выполни `git status`: в дереве работают и другие сессии, и их изменения не должны пропасть. Pull делай, только когда дерево чистое.
2. **Добавь в `backend/.env`:**
   ```
   TRANSPORT_API_URL=https://10.10.11.79:8444/api/v1/external
   TRANSPORT_API_KEY=<ключ, как сейчас>
   TRANSPORT_API_MODE=mock
   TRANSPORT_API_VERIFY_TLS=false
   ```
3. **Выполни миграции и правила задач** (они пишут в общую dev-базу):
   ```
   cd backend
   python manage.py migrate core transport export
   python manage.py seed_task_rules
   ```
   Проверь, что применились: `python manage.py showmigrations core transport export | findstr "0070 0009 0010 0091"`. Все четыре строки должны быть отмечены `[X]`.
4. **Запусти backend и frontend** как обычно (runserver + `npm run dev`).
5. **Опрос Planning** можно запускать двумя способами.
   - **Вручную (удобнее для проверки):** это один тик опроса — рейсы подтягиваются и сразу применяются изменения.
     ```
     python manage.py shell -c "from apps.transport.tasks import poll_external_trips as p; print(p())"
     ```
     Результат выглядит так: `{'ok': True, 'changed': N}`.
   - **Автоматически:** запусти Celery worker и beat (на Windows: `celery -A config worker -P solo` и `celery -A config beat`). Тогда тик идёт сам раз в 2 минуты.
6. **Подготовь пользователей для проверки прав:** `export_manager` (главный), `document_team`, `transport`, `sales_rep`, `garawul`. Удобно держать два браузера или окно инкогнито.
7. **Подготовь отгрузки.** Нужны 2–3 обычные (не gapy) отгрузки в статусе **Preparation (`draft`)** с заполненной **страной KZ или RU**, клиентом и блоками. Можно взять существующие или создать через черновики и Join.
   - Рейсы в mock: 2 в KZ, 1 в UZ, 2 в RU (всего 6). Выбирай страну отгрузки так, чтобы для неё были рейсы.

**UUID рейсов в mock** (для `simulate_trip_change`):

## 2. Как работать с чек-листом

Иди по сценариям по порядку: следующие опираются на данные предыдущих. На каждом шаге сверяй написанное после «→» с тем, что видишь. Не совпало — запиши номер шага, роль и скриншот.

---

## 3. Сценарии

### A. Доска открывается и видит рейсы
1. Сделай один тик опроса (п. 1.5).
2. Войди как `export_manager` → меню «Доставка» / «Экспорт» → **Maşynlar ↔ Ugratmalar** (`/export/truck-board`).
   - → Сверху справа тег **Demo** (значит, режим mock) и строка «Синхронизация N мин назад».
   - → Слева «Отгрузки без машины»: твои обычные черновики. Gapy-отгрузок там **нет**.
   - → Справа «Запланированные машины»: 6 рейсов.

### B. Фильтр по стране
1. Кликни отгрузку со страной KZ.
   - → Справа остаются рейсы в KZ. Рейсов в RU и UZ не видно.
2. Кликни ту же отгрузку ещё раз, чтобы снять выбор, затем кликни рейс в RU.
   - → Слева остаются только отгрузки в RU.

### C. Карточка и детали рейса
1. На карточке рейса проверь:
   - → номер тягача и прицепа, водителя, тег «Свой парк» или «Сторонний», страну;
   - → строку 📍: место и «N мин назад», если у тягача есть GPS, иначе «Нет GPS».
2. Выбери отгрузку KZ и посмотри на рейс `1234AGG` (сторонний водитель без виз).
   - → Тег **⚠ Нет визы**.
3. Нажми «Подробнее» на любом рейсе.
   - → Справа выезжает панель: паспорт и срок действия, визы (страна и дата), статус рейса **словами** («Создан», а не `CREATED`), мини-карта, если есть GPS.
4. Нажми «Документы рейса (PDF)».
   - → Открывается новая вкладка с PDF. В mock это пустой лист, в live — лист A4 со сканами.
   - → Браузер **не** блокирует всплывающее окно.

### D. Привязка рейса к отгрузке
1. Выбери отгрузку KZ, затем рейс KZ `2546AHF`, нажми **Привязать**.
   - → Всплывает «Машина привязана к <код отгрузки>».
   - → Отгрузка ушла из левой колонки, рейс — из правой.
   - → Во вкладке **Привязанные** появилась строка с этой парой.
2. Открой эту отгрузку на **странице отгрузки**, карточка «Транспорт».
   - → Сверху синий тег «Рейс: ожидает кода», статус рейса, кнопка PDF.
   - → Номер машины `2546AHF/2296TAH`, водитель, телефон.
   - → Строка «Паспорт действителен до 2028-03-15».
   - → Выбор машины и водителя, а также поля телефона и паспорта **серые, их нельзя менять**.
3. Открой **Sheet** и найди колонку этой отгрузки.
   - → Ячейки номера машины, водителя и телефона не редактируются: ни кликом, ни вводом, ни Ctrl+V, ни Delete.
   - → Другие ячейки, например погранпереход, редактируются.
4. Открой **Мои задачи** под `export_manager`.
   - → У этой отгрузки задача «Выбрать машину (рейс)» **закрыта**.
   - → У новой обычной отгрузки задача «Выбрать машину (рейс)» висит открытой.
   - → Задачи «Назначить водителя» у обычных отгрузок больше нет.

### E. Рейс без страны
1. Пропусти, если во всех рейсах страна заполнена. В mock она есть у всех. Проверить можно так: временно убери `destinationCountryCode` у одного рейса в fixture, затем сделай тик опроса.
   - → Рейс стоит серым в группе «Страна рейса не указана».
   - → При привязке спрашивает «Страна рейса не указана. Всё равно привязать?». Ответ «Да» привязывает, «Нет» — нет.

### F. Два менеджера привязывают один рейс
1. Два браузера под разными `export_manager`. Оба выбирают один и тот же свободный рейс, каждый со своей отгрузкой. Нажимают «Привязать» почти одновременно.
   - → У первого привязалось.
   - → Второй видит «Эта машина уже привязана». Нет белого экрана и нет ошибки 500.

### G. Права
1. `transport`: доска открывается, всё видно.
   - → Кнопок «Привязать», «Отвязать», «Перенести», «Принять» нет, или они неактивны.
2. `sales_rep`: пункта меню нет; прямой адрес `/export/truck-board` ведёт на «Нет доступа».
   - → На странице отгрузки с рейсом плашка рейса **видна** (номер рейса, статус, PDF).
3. `garawul`: открой в браузере `/api/v1/transport/shipments/<id отгрузки из D>/trip/`.
   - → **403**. Охрана не видит паспорта и телефоны водителей.

### H. Planning поменял водителя, отгрузка ещё в Preparation
1. ```
   python manage.py simulate_trip_change b242b4de-a941-4dba-899e-3b0235e9f4ec --driver "Täze Sürüji"
   ```
   затем один тик опроса.
   - → На странице отгрузки водитель стал «Täze Sürüji». Статус не изменился (Preparation).
   - → В комментариях отгрузки системная запись: «Planning changed the trip: … → …».
   - → У `export_manager` колокольчик: новое уведомление по этой отгрузке.
   - → Красной плашки нет: изменение применено, конфликта нет.

### I. Planning поменял машину, а отгрузка уже на таможне (откат)
1. Возьми другую привязанную отгрузку (привяжи новую, как в D). Доведи её до **Gümrük giriş** или **Gümrük çykyş** обычным путём: документы → ready и т. д.
2. ```
   python manage.py simulate_trip_change bcf69fba-c7dc-48df-b0ae-1367f0a48da5 --tractor 9999AHF
   ```
   (подставь UUID рейса, привязанного к этой отгрузке), затем тик.
   - → Статус отгрузки вернулся в **Preparation (`draft`)**.
   - → Номер машины стал `9999AHF/...`.
   - → «Статус документов» стал **in_progress**. Задача подготовки документов снова открыта.
   - → Если откат был с Gümrük çykyş: поле «Выезд с таможни» очищено, в истории изменений (audit) видно старое значение.
   - → Уведомление пришло `export_manager` **и** `document_team`.
3. Сохрани у этой отгрузки любое постороннее поле, например телефон, если он не заблокирован, или любую свою ячейку.
   - → Статус **остаётся** Preparation и сам на таможню не уходит.
4. Снова поставь «Статус документов» = ready.
   - → Отгрузка переходит **только** в Gümrük giriş, а не сразу в Gümrük çykyş.

### J. Planning поменял водителя, а погрузка уже началась (конфликт)
1. Возьми привязанную отгрузку в статусе **Ýüklenme** с заполненным «Начало погрузки» или уже **Ýola çykdy**.
2. `simulate_trip_change <uuid этого рейса> --driver "Başga Sürüji"` → тик.
   - → Водитель в отгрузке **не** поменялся. Статус не поменялся.
   - → На странице отгрузки красная плашка: «Planning сменил машину: <было> → <стало>», на языке интерфейса.
   - → На доске во вкладке «Привязанные» красный тег конфликта.
3. Нажми **«Принять изменение»** на плашке или во вкладке.
   - → Водитель стал новым, плашка исчезла, статус **не** поменялся.

### K. Planning отменил рейс
1. **Отгрузка в Preparation:** `simulate_trip_change <uuid> --cancel` → тик.
   - → Рейс отвязан: поля машины и водителя пустые, задача «Выбрать машину (рейс)» снова открыта.
   - → Отгрузка снова слева на доске.
2. **Отгрузка уже выехала:** то же самое, `--cancel`.
   - → Конфликт (красная плашка «Planning отменил рейс»), связь осталась.
   - → После «Принять»: рейс отвязан, поля пустые, но задача «Выбрать машину» **не** открывается снова: отгрузка уже в пути.

### L. Отвязать и перенести вручную
1. Вкладка «Привязанные» → **Отвязать** у отгрузки в Preparation → подтвердить.
   - → Связь снята, отгрузка снова слева, задача «Выбрать машину» открыта.
2. **Перенести**: выбери другую отгрузку той же страны.
   - → Рейс теперь у новой отгрузки, старая свободна.
3. Отвязать у отгрузки на таможне.
   - → Отгрузка откатывается в Preparation (как в I).
4. Отвязать у выехавшей отгрузки.
   - → Отказ: «Отгрузка заблокирована — погрузка началась».

### M. Что мы отправляем в Planning
1. В mock отправка только пишется в лог Celery / runserver: строки `MOCK push <uuid> export-code ...` и `... loading ...`.
   - → Сразу после привязки уходит одна строка `export-code`, если у отгрузки есть код экспорта, и одна `loading`: город погрузки и **названия** блоков.
2. Измени код экспорта у привязанной отгрузки в Sheet → тик.
   - → Одна новая строка `export-code` с новым кодом, **одна**, не на каждом тике.
3. Добавь или убери блок у привязанной отгрузки → тик.
   - → Одна новая строка `loading`.

### N. Gapy satyş не изменился
1. Открой gapy-отгрузку.
   - → На доске её нет.
   - → В Sheet водитель по-прежнему вводится вручную (ФИО, телефон, паспорт, дата выдачи).
   - → Задача «Назначить водителя» (для document_team) у gapy **осталась**.

### O. Язык
1. Переключи язык на **Türkmen**, потом на **Русский**.
   - → Доска, плашка конфликта, статусы рейса, ошибки — всё на выбранном языке. Английского текста и кодов вроде `DOCUMENTS_READY` нигде не видно.

### P. Planning недоступен
1. В `.env` поставь заведомо неверный `TRANSPORT_API_URL`, поставь `TRANSPORT_API_MODE=live`, перезапусти backend и сделай тик.
   - → Результат тика: `{'ok': False, ...}`.
   - → На доске жёлтая плашка «Planning не отвечает — показаны последние полученные рейсы». Старые рейсы на месте.
2. Верни `.env` как было.

## 4. После проверки

1. Верни fixture: `git checkout backend/apps/transport/fixtures/external_trips.json`.
2. Если всё прошло, отметь в `BUILD_TEST_LOG.md` строку «Truck Board + Planning trips integration»: `- [ ]` → `- [x]` и `— TESTED`.
3. Ошибки запиши в формате «сценарий / шаг / роль / что ожидалось / что увидел» и отдай мне.

## 5. Коротко в live (после mock)

1. В `.env` поставь `TRANSPORT_API_MODE=live` с верным URL и ключом. Перезапусти backend и сделай тик.
   - → Тег Demo пропал. Рейсы — настоящие из Planning, сейчас там 6 тестовых.
   - → Страна у рейсов подтянулась: список Planning её не отдаёт, мы берём её из запроса деталей рейса.
2. Привяжи **один тестовый** рейс к тестовой отгрузке.
   - → В Planning (`GET /trips/{uuid}`) через 1–2 минуты `tripNumber` = наш код экспорта, `loadingCity` = наш город погрузки.

Реальные рейсы не трогай, пока Planning не отметит заказчика «работает через внешнюю программу» для боевых рейсов.
