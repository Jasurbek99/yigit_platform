Дата: 2026-09-18. Писалось как анализ без изменений кода; вариант A сделан в тот же день (см. §8).

Источники (все запросы — GET с Bearer-токеном к `http://10.10.11.79:8082/api`):
`/geofences`, `/positions`, `/devices`, `/notifications`,

## 1. Что возвращает `/api/geofences`

- **31 геозона**, все в формате `POLYGON` WKT (5–12 точек).
- Координаты идут **сначала широта** — `POLYGON ((38.078 62.755, ...))`. Это соглашение Traccar,
  обратное стандартному WKT (долгота, широта). Любой парсер должен менять их местами.
- Поля: `id`, `name`, `area`, `description` (везде null), `calendarId` (везде 0), `attributes` (везде `{}`).
  **Нет метаданных типа/категории** — платформе придётся классифицировать геозоны самой.
- id от 3 до 43 с пропусками (часть удалена в Traccar).
- id 3 — `Garaž` (UTF-8 `ž`), депо YGT.

## 3. Работает ли это сейчас? Да

- Traccar уже сам определяет вхождение в геозоны: **63 из 92** текущих позиций содержат `geofenceIds`.
- **572 события входа/выхода за 7 дней** от 37 из 122 устройств. Traccar сохраняет их независимо от того,
  настроено ли уведомление.
- В `/api/notifications` **только одно правило** (`deviceOverspeed`, web). Нет уведомлений по геозонам и нет
  вебхука → ничего не отправляется нам само. Единственный путь без изменения настроек Traccar — опрос (polling).
- Статус устройств сейчас: 25 онлайн, 80 офлайн, 17 неизвестно.

## 6. Сопоставление с таймстампами жизненного цикла v2

В v2 эти таймстампы — **триггеры авто-перехода статуса** (см.
[shipment-lifecycle.md](obsidian/processes/shipment-lifecycle.md)). Запись поля двигает статус.

| Поле (строка Sheet) | Переводит в | Кандидат-геозона | Вывод |
|---|---|---|---|
| `loading_started_at` (R19) | → `yuklenme` | вход в Kaka / Dushak parnik | **Частично.** Геозоны только у 2 мест погрузки. |
| `departed_at` (R21) | → `yola_chykdy` | выход из теплицы / выход из Garaž | **Неоднозначно.** Машина может ехать теплица → депо → таможня. |
| `customs_exit_at` (R25, таможня TM) | → `gumruk_chykysh` | выход из Gumruk | **Слабо.** Медиана стоянки в Gumruk 0,0 ч на 28 визитов (в основном проезд). |
| `border_crossed_at` (R30) | → `serhet_gechdi` | выход из Farap gumruk / выход из Turkmen-Gazak gumruk | **Хорошо.** Компактные пограничные полигоны. |
| `dest_entry_at` (R31) | → `dest_entry` | вход в Olot gumruk (UZ) / вход в Ozinki (RU) | **Хорошо для UZ и RU.** Для KZ Turkmen-Gazak — один полигон на обе стороны. |
| `customs_entry_at` (R32, таможня назначения) | → `barysh_gumrugi` | — | **Пробел.** Таможенные терминалы назначения не размечены геозонами. |
| `arrived_at` (R35) | → `bardy` | вход в Food city / город назначения | **Food city — да;** городские полигоны слишком крупные (Almaty 44×70 км). |

## 7. Оговорки

1. **У событий нет направления.** Обратный рейс TR060 генерирует тот же `geofenceEnter`, что и
   гружёная машина, идущая туда. Любое использование нужно ограничивать статусом и временным окном
   связанной отгрузки, а не только геозоной.
2. **Автозапись двигает статус.** Так как в v2 таймстампы — триггеры, ошибочное GPS-событие продвинет
   отгрузку вперёд. Безопаснее «предложить → оператор подтверждает», чем писать молча.
3. **Перегруз разрывает связь.** После перегрузки груза на другую машину связанное устройство
   больше не следует за томатами.
4. **Опрос может пропустить быстрые точки.** Сравнение `geofenceIds` между опросами раз в 120 с пропускает
   проезды длительностью 0,0 ч; `/api/reports/events` — нет (95 КБ/неделя по всем 122 устройствам за один запрос).
5. **Покрытие неизвестно.** В `YIGIT_PLATFROM_NEW` за последние 7 дней отправлено только 2 отгрузки. Обе
   автоматически сопоставлены с устройством (`resolve_device_for_shipment`), и у 1 из 2 устройств есть
   события геозон. Слишком мало для выводов — перемерить в сезон.
6. Токен всё ещё от админа Traccar (уже известный отложенный пункт).
