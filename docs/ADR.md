# Architecture Decision Records

## ADR-001: MSSQL Database
**Decision**: Use MSSQL via `mssql-django`. Required for Logo Tiger ERP compatibility.
**Consequences**: No JSONField/ArrayField, no DISTINCT ON, 2,100 param limit. Workarounds in `mssql-compat.md`.

## ADR-002: Shared Core App
**Decision**: `core/` Django app holds shared reference models. All other apps import from core, never reverse.
**Consequences**: core/ changes affect all modules. Core models should be stable.

## ADR-003: Status Machine via FK + Log Table
**Decision**: `status_id` FK on shipment + `shipment_status_log` audit table. Transitions via `transition_to()` method. Transition rules in Python TRANSITIONS dict (DB `shipment_status_types` for reference data only).
**Consequences**: Single source of truth. Full audit history. Business logic centralized.

## ADR-004: API-First Design
**Decision**: Every feature has a REST API. React frontend is one consumer. Mobile CRM will reuse same API.

## ADR-005: Mock Data Development Mode
**Decision**: `VITE_USE_MOCK=true` flag. Frontend hooks return mock data from `src/mock/`.

## ADR-006: Ant Design 5 + ProTable
**Decision**: Ant Design 5 for all UI. ProTable for data tables. Enterprise data-heavy use case.

## ADR-007: TanStack Query for Server State
**Decision**: TanStack Query for API data. Zustand only for UI state (sidebar, locale, filters).

## ADR-008: Docker Compose Deployment
**Decision**: 5 services: Django, React (Nginx), MSSQL, Redis, Nginx. Company server, no cloud.

## ADR-009: httpOnly Cookie Authentication
**Decision**: JWT stored in httpOnly cookie, not localStorage. Backend sets cookie with `httpOnly=True, Secure=True, SameSite=Lax`. CSRF token on mutations.
**Context**: Sales reps in KZ/RU use public networks. httpOnly cookies cannot be stolen via XSS.
**Consequences**: Frontend never touches the token. Need CSRF protection. Mobile CRM will need separate token flow.

## ADR-010: Denormalized Timestamps (AD-1)
**Decision**: 8 timestamp columns on `export.shipments` (`loading_started_at` through `sale_ended_at`). Written ONLY by `transition_to()`, never directly.
**Context**: List views need departure/arrival dates without joining to status_log.
**Consequences**: Fast list queries. Small staleness risk (mitigated by single write path via `transition_to()`).
**2026-05 amendment (final)**: AD-1 is retired. Every lifecycle timestamp — `loading_started_at` (R19), `departed_at` (R21), `customs_exit_at` (R25), `border_crossed_at` (R30), `customs_entry_at` (R32), `arrived_at` (R35), `sale_started_at` (R41), `sale_ended_at` (R42) — is operator-entered on the Sheet (`input_type='datetime'`). `STATUS_TIMESTAMP_MAP` is empty; `transition_to()` still updates `status` + `status_changed_at` but no longer stamps any column. `ShipmentPatchSerializer` accepts all eight. Practical reason: warehouse / transport / document / sales staff fill these from physical events (gate stamp, door closed, customs receipt, sale concluded) that don't line up with the moment they click "Next status" — they need the actual time, not `timezone.now()`. The original AD-1 staleness mitigation ("single write path via transition_to()") is gone; data quality now depends on operators filling the cells correctly. Downstream readers (boss analytics' "loaded today", transit-day calculations) will see null for timestamps an operator hasn't filled yet.

## ADR-011: R15 Replacement (AD-2)
**Decision**: Kill `vehicle_status_note` free-text field. Replace with `vehicle_condition` (enum: OK/ISSUE/BREAKDOWN/RETURNED), `vehicle_condition_note`, `route_note`. Freeform notes go to `shipment_comments` table.
**Context**: R15 field degrades into notepad used by everyone with no attribution.
**Consequences**: Structured, queryable vehicle data. Comments system with @mentions and threading. Old R15 data migrates as first comment per shipment.

## ADR-015: Cell-Anchored Comments + Tasks
**Decision**: Extend `export.shipment_comments` with: `field_key` (cell anchor; NULL = shipment-level), `role_mentions` (CSV separate from user-ID `mentions`), and task fields `assignee`/`is_done`/`done_at`/`done_by`. Mentions fan out into the existing `Notification` model (extended with `mention`, `task_assigned`, `task_done` kinds). Sidebar UI is a right-side `Drawer` on the [[../docs/obsidian/screens/shipment-sheet|Sheet]] — not a permanent Splitter pane.
**Context**: AD-2 (ADR-011) created the `shipment_comments` table but kept comments shipment-level. Operational reality from the Sheet (rows × shipment-columns) needs comments pinned to specific cells (e.g. "wrong weight on R32") and the ability to turn a comment into a single-assignee task without spinning up a separate task service.
**Decisions locked with users (Apr 2026)**:
1. Cell mentions are **both** anchor (pin to cell, sidebar filters by selected cell) and reference (`#cell:fieldKey` token in body renders as a clickable chip).
2. Role mentions notify **every active member of the role, deduped** with explicit user mentions — one notification per recipient per comment.
3. **Tasks live on root comments only**, single assignee. Replies inherit parent's `field_key` and cannot have their own assignee.
4. Sidebar is a **toggle Drawer** (not a Splitter) — the Sheet is column-dense; permanent horizontal real-estate loss is unacceptable.
**Consequences**: One model, no separate `Task` table. CSV pattern for `role_mentions` mirrors existing `mentions` (MSSQL-safe per ADR-001). Notification fan-out is a single `bulk_create(batch_size=500)` per comment — see `apps/export/services/comments.py`. Polling cadence stays at 30s (no WebSockets — see ADR-008 for the no-cloud constraint). The legacy `POST /shipments/{id}/comment/` action delegates to the new service so callers don't break. Deep-link format `/export/shipments/sheet?shipment=&row=&comment=` is canonical for all three new notification kinds. Resolution / multi-assignee tasks / file attachments / WebSockets are explicitly **out of scope** for v1.

## ADR-012: Weekly Plan 12 Columns (AD-3)
**Decision**: `export.weekly_harvest_plans` keeps 12 columns (monday_plan_kg through saturday_actual_kg). Not normalized to rows per day.
**Context**: 15 blocks x 6 days entered once weekly. Simplicity wins.
**Consequences**: Fast 15x6 grid rendering. Sunday support = add 2 columns via migration if needed.

## ADR-013: Explicit Services, Not Signals
**Decision**: Cross-app business logic uses explicit service calls, not Django signals.
**Context**: Signals are implicit, hard to debug, fail silently.
**Consequences**: Slightly more boilerplate but fully traceable execution.

## ADR-014: DRAFT Shipment Status (Pre-Lifecycle Step 0)
**Decision**: Add a `draft` row to `ShipmentStatusType` with `step_order=0`. A shipment with `status=draft` has block_sources and total weight fixed, but country/customer/city left null. Soltanmyrat (warehouse_chief) creates drafts; Gadam (export_manager) transitions `draft → yuklenme` via `POST /shipments/{id}/assign/`, which writes AD-1 `loading_started_at` through `transition_to()`.
**Context**: Kaka site visit (Apr 2026) revealed shipment creation is inherently two-person, two-moment: Phase 1 (Soltanmyrat ~9–10am) fixes supply composition without destination context; Phase 2 (Gadam ~10–11am) matches drafts to contracts/quotas/waiting customers. A single-form design forces one role to fabricate the other's data. `ShipmentBlockSource` already supported multi-block composition — only a new status and a dedicated assign endpoint were missing.
**Consequences**: Two-phase creation matches operational reality. `draft` has no AD-1 timestamp (lifecycle timestamps still start at `yuklenme`, preserving AD-1). Existing `ShipmentList`/`KanbanBoard`/filters are unaffected — draft shipments appear in any `?status=draft` query but are hidden from the default lifecycle Kanban by excluding that status. Does not address Findings #3 (variety-at-packaging), #4 (pallet manifest + weight_master), #5 (Soltanmyrat 5-function role + truck dispatch), #6 (received-weight productivity) — tracked separately.

## AD-15: System admin role separated from director / export_manager
**Decision**: A new top-tier `admin` role owns system-administrator capabilities only — managing the permission matrix (`/api/v1/core/admin/page-permissions/`, `resource-permissions/`, `field-permissions/`, `permission-registry/`) and managing users (`PATCH users/{id}/`, `PUT users/{id}/permissions/`). `director` and `export_manager` retain every operational capability they had before — full CRUD on shipment / quota / plan / price / report resources, wildcard `*` field edits, reference-data writes (countries, cities, customers, blocks, etc.) — and lose only the admin pages. A last-admin guard prevents demoting or deactivating the only active admin in the system. Admin promotion is operator-driven via `python manage.py bootstrap_admin` (idempotent, promotes every `is_superuser`); no auto-promotion data migration runs across environments.
**Context**: Pre-AD-15 the closest thing to a system administrator was `director`, hardcoded into `_DirectorOnlyPermission` and into reference-data writes in `core/views.py` and `greenhouse/views_admin.py`. `export_manager` was seeded with near-admin power: full CRUD on every resource, wildcard field edits, and the `admin.permissions` page in its default visibility set (the backend rejected saves but the page was reachable). The user (system administrator / developer) wanted to be the sole permission-editing principal while keeping a separate operational coordinator (`export_manager`) and the company owner (`director`) below the admin tier. Reference-data writes are operational, not administrative — adding a new customer or city should not require waking the admin.
**Consequences**: Future contributors must not gate operational capabilities behind `_ADMIN_ONLY` — only permission-matrix / user-management endpoints belong there. `REFERENCE_DATA_WRITE = frozenset({'admin', 'director', 'export_manager'})` is the canonical reference-data gate; expanding it (e.g. adding a new operational role that needs to create customers) requires updating one constant. The data migration `0016_demote_existing_director` removes the seeded admin.* rows from director and admin.permissions from EM — this runs automatically on every `migrate` so existing environments inherit the new behaviour without manual intervention. `seed_permissions` is non-destructive (`get_or_create`) — re-running it adds new admin rows but does NOT undo the migration's deletes. Director keeps the hardcoded sheet-cell trigger-gate immunity in `permissions.py:can_edit_sheet_field` (operational lead must remain immune to `SheetRowSetting` triggered_role locks); admin is added alongside, not replacing. `IsBossOrDirector` includes admin despite the name; rename filed as a follow-up. `loading_dept_head` is intentionally absent from `apps/export/services/comments.py:_VALID_ROLES` — pre-existing inconsistency, separate cleanup.

## ADR-016: Official vs Real Truck Weight (Firm Splits)
**Decision**: `ShipmentFirmSplit.weight_kg` is the **OFFICIAL** kg per firm written on export documents — it is **not** the real truck weight. The official cap is 18,100 kg per truck. Real trucks carry 20,000–21,000 kg, but the cap is what regulators see, so the cap is what the platform persists. The per-firm-count split is admin-configurable via the `TruckSplitDefault` model (defaults: 1→18,100 · 2→9,000 · 3→6,000), edited at `/admin/shipment-settings → Truck Split Defaults`. The `set_firm_splits` action endpoint auto-fills `weight_kg` from this table when the client omits it. `ShipmentBlockSource.weight_kg` follows a different rule — it splits the **real** `Shipment.weight_net` evenly (last entry takes the remainder), because blocks track real harvest contribution, not regulatory paperwork.
**Context**: User confirmed (Apr 2026) that the platform's previous behaviour — frontend hardcoding `weight_kg: 0` on the Sheet's R8/R9 multiselect — was breaking every Sum-of-block-weight aggregation in the Boss dashboard. The fix needed two distinct rules because the two cells have different meanings: blocks are real, firms are regulatory. The `get_default_truck_weight()` helper already encoded the firm rule for `QuotaUsageRecord` auto-creation but was hardcoded in Python; the requirement was to make it admin-editable without a deploy.
**Consequences**: Future contributors must not "fix" the gap between `Sum(firm_splits.weight_kg)` ≈ 18,100 and the real `Shipment.weight_net` ≈ 18,500–21,000 — that gap is intentional. `get_default_truck_weight(N)` now reads from `TruckSplitDefault` with a 5-min cache; admin saves invalidate via `invalidate_truck_split_cache()`. Director gets full CRUD on `truck_split_default`; export_manager is read-only. Existing client code that explicitly sends `weight_kg` is honoured (admin override path). A new `truck_split_default` resource is added to `permission_registry.py` and seeded in `seed_permissions`. Replaces the previous hardcoded `DEFAULT_TRUCK_WEIGHTS` Python dict.


## ADR-017: Daily-Grain `HarvestDayEntry` (supersedes ADR-012)
**Decision**: The daily harvest data — Plan, Forecast, Actual — moves from twelve wide columns on `WeeklyHarvestPlan` (`monday_plan_kg` … `saturday_actual_kg`) into a daily-grain table `export.harvest_day_entries`, one row per `(weekly_plan, entry_date)`. Each row holds `plan_value` / `forecast_value` / `actual_value` plus per-layer audit columns: `*_submitted_at`, `*_submitted_by`, `plan_state`, `forecast_window`, `forecast_revision_count`, `actual_finalized_at`, `actual_source`, `last_override_at` / `_by` / `_reason`. `weekday` allows 0–6 so end-of-season Sunday harvesting is supported. `WeeklyHarvestPlan` survives as the per-week submission container (id, season, block, week_number, year, submitted_at, submitted_by, locked_at, entered_by, created_at, updated_at) — the approval workflow (status / approved_at / approved_by / rejected_at / rejected_by / rejection_note) is removed.

**Context**: ADR-012 chose 12 wide columns "for fast 15×6 grid rendering" with the explicit note that "Sunday support = add 2 columns via migration if needed". The Forecast Layer feature (Apr 2026) needed three values per cell (Plan, Forecast, Actual) plus per-cell audit fields (timestamps, submitters, submission-window state, revision counts) so that historical data needed for KPIs is captured from day one. Extending the wide-column design would add 60+ columns to the table; the alternative — JSONField — is forbidden per ADR-001 (MSSQL). A daily-grain row matches the per-cell audit requirement directly and makes the cell-history modal a simple key lookup. The user also chose "remove approval workflow — submission is final" and "atomic cutover migration", so the wide columns and approval fields ship out in the same migration that introduces the new table.

**Consequences**: ADR-012 is superseded. Future contributors must not "optimize" by re-flattening to wide columns — the audit fields cannot fit. Plan vs. Forecast vs. Actual semantics are decoupled per cell: empty (`value IS NULL`) renders as em-dash; explicit zero (`value = 0 AND *_submitted_at IS NOT NULL`) renders italic with confirmation indicator. `plan_state` (`on_time` / `late` / `critical_late`) is computed by `compute_plan_state(submitted_at, plan_week_start, config)` from `GreenhouseConfig`-driven deadlines; `forecast_window` (`primary` / `fallback` / `same_day_red_flag`) is computed by `compute_forecast_window(submitted_at, entry_date, config)`. Admin overrides (with required `reason`) write to `AuditLog` AND to the `last_override_*` snapshot for fast cell-history modal access. Time-based notification dispatch runs via `python manage.py run_harvest_dispatcher` from system cron every 5 minutes, idempotent via `HarvestDispatchLog(trigger_kind, target_user, scope_date)` UNIQUE — chosen over Celery+Redis (overkill for ≤90 trigger events/day) and Django-Q2 (introduces a queue concept nothing else needs yet); revisit when pallet rollup arrives. The personal kanban auto-task hook is a TODO no-op call site in the dispatcher — the five harvest auto-task rules land in a follow-up commit when the parallel kanban work ships. `truck_capacity_kg` (was hardcoded 18,500 in frontend) moves to `GreenhouseConfig` so it's admin-tunable without a deploy. Existing data backfill (greenhouse migration `0004`): explodes 333 weekly rows into 1,998 day-entry rows, preserving the "never entered" semantic by leaving `plan_value=NULL` where the wide column was 0 AND `submitted_at IS NULL` (257 NULL / 1,741 valid). KPI computation is deferred to a later phase but every audit field needed is captured from day one.


## ADR-018: State Machine v2 + Field-Trigger Auto-Advance
**Decision**: Restructure the 13-step shipment lifecycle into a 12-step v2 machine where every status corresponds to one operator-entered field on the Sheet. When the trigger field for the current step fills, `Shipment.save() → auto_advance_if_ready()` fires `transition_to(next_step, is_auto=True)` automatically. The role gate is bypassed for auto-transitions; `ShipmentStatusLog.is_auto=True` records the system origin.

New chain (no-peregruz):
`draft → gumruk_girish → gumruk_chykysh → yuklenme → yola_chykdy → serhet_gechdi → dest_entry → barysh_gumrugi → bardy → satylyar → satyldy → tamamlandy`

Conditional fork at `barysh_gumrugi` when `has_peregruz=True`: `barysh_gumrugi → transshipment → bardy`. The fork is encoded as an optional 3rd element on `TRANSITIONS` edges — `Callable[[Shipment], bool]` — evaluated by a new `_resolve_next_status()` helper. Manual transitions ignore predicates; only auto-advance evaluates them.

**Yuklenme moves from step 1 to step 3** (after both customs steps). Operationally correct: TM customs documents are pre-cleared while the truck physically loads at the greenhouse — by the time loading starts, paperwork is in motion.

**Merges**: `serhet_tm + serhet_gechdi → serhet_gechdi`, `hasabat + tamamlandy → tamamlandy`. The retired codes (`serhet_tm`, `yolda`, `hasabat`) stay in `ShipmentStatusType` with `is_active=False` at `step_order=100+` for audit reference. Migration `export.0021_remap_retired_statuses` shifts any existing shipments at retired codes to their nearest active equivalent (`serhet_tm → serhet_gechdi`, `yolda → barysh_gumrugi`, `hasabat → tamamlandy`) and appends a `is_manual_override=True` audit log row per shifted shipment.

**Customs Entry trigger is value-specific**: fires on `documents_status == 'in_progress'`, not on any non-empty value. Implemented via a new `TaskCompletionRule.FIELD_EQUALS` + `target_value` column on `TaskRule`/`Task`.

**Context**: Operators were already filling Sheet cells (loading time, departure time, border crossing, arrival, sale start/end, report date) — each completion was naturally meaningful as "this step is done." The pre-v2 flow required a second click on the TransitionButton to advance status, which was friction with no information value. The redesign also collapsed two intermediate stations that didn't represent distinct work (`serhet_tm` was an intermediate "at the border but not crossed" sub-state that nobody updated), and made conditional flows explicit (`has_peregruz` shipments transit through `transshipment`, others skip).

**Consequences**: AD-1 (ADR-010) is consistent with v2 — every lifecycle timestamp is now operator-entered; `STATUS_TIMESTAMP_MAP` is empty. The Task Engine (already auto-resolving tasks via `Shipment.save() → resolve_for_shipment()`) is reused as the gating mechanism: when every non-`MANUAL_DONE` Task for the current step is DONE, auto-advance fires. `MANUAL_DONE` tasks remain operational reminders only — they never gate auto-advance. Re-entry is guarded by a thread-local flag — strictly one transition per outer save (so `transition_to()`'s inner `shipment.save()` cannot cascade). Concurrent-edit race losers raise `ValueError` internally and are logged. `is_step_trigger_satisfied()` requires at least one active non-`MANUAL_DONE` TaskRule on the step — a step with zero rules is never auto-advanced (vacuous-truth guard). `create_shipment()` always starts at `code='draft'`. `/assign/` endpoint now promotes `draft → gumruk_girish` (was `→ yuklenme`). Frontend `RouteTimelineRail` conditionally splices `transshipment` based on `has_peregruz`; `dest_entry` label appends the country name. Phase mapping (`services/phases.py`) deliberately unchanged. Tests in `tests_auto_advance.py` cover FIELD_EQUALS, peregruz fork, re-entry guard, and the no-rules guard.


## ADR-019: Shipment Cancellation as a 14th Terminal Status
**Decision**: Add a `cancelled` row to `ShipmentStatusType` (`step_order=99`, `phase='CANCELLED'`, `is_active=True`, `trigger_field=None`) reachable from every non-terminal status. The v2 `TRANSITIONS` dict gains one cancel edge per active status — `('cancelled', list(PRIVILEGED_ROLES))` — on all 12 statuses from `draft` through `satyldy`; `tamamlandy` (completed) gets none. `cancelled` is itself terminal (no outgoing edges) and has no trigger field, so auto-advance can never fire from or into it. Cancellation is exposed as a **dedicated** action `POST /api/v1/export/shipments/{id}/cancel/` with a required `reason`, not via the generic `/transition/` endpoint. Only `export_manager` and `director` (`PRIVILEGED_ROLES`) may cancel. The reason is stored as the `ShipmentStatusLog` comment on the cancel transition — no new column. On cancel, open / in-progress / blocked `Task` rows are bulk-set to `CANCELLED` (state column only — `Task` has no per-row cancel-audit columns); comments are preserved; draft `QuotaUsageRecord` rows linked to the shipment are deleted and approved ones are returned in the response (`approved_quota_to_reconcile`) for manual reconciliation. Cancelled shipments are excluded from the operational list by default (`?show_cancelled=true` or `?status_code=cancelled` reveals them; the exclude is scoped to the `list` action so detail pages stay reachable) and never appear on the Kanban board (no `CANCELLED` phase column). `cancelled` is filtered out of the serializer's `allowed_transitions` so the forward TransitionButton never offers it.

**Context**: The v2 state machine (ADR-018) is a strictly forward chain with no exit valve. Real operations need to abandon shipments mid-lifecycle — broken truck before customs, customer cancellation after sale, regulatory rejection at the border, quality failure on arrival. The only prior options were to leave a dead shipment hanging in an intermediate status forever (clutters every view, emits spurious overdue tasks, never satisfies auto-advance) or hard-delete it (destroys the audit trail). A terminal `cancelled` status preserves the full audit trail and comments while removing the shipment from active work. A dedicated endpoint (rather than a `cancelled` entry in the forward dropdown) was chosen so the reason can be made mandatory without tightening the general `/transition/` contract, and so the destructive action gets a distinct red-button + confirm-modal UX. While implementing, a pre-existing latent bug surfaced and was fixed: `get_allowed_transitions` unpacked edges as 2-tuples and crashed on the `barysh_gumrugi` 3-tuple conditional edges — rewritten to use `_edge_to()`.

**Consequences**: Future contributors adding a status must decide whether it accepts a cancel edge — terminal statuses never do. The cancel role gate reuses `PRIVILEGED_ROLES`; since privileged users already bypass the per-edge role check in `transition_to()`, the edge's role list (`['export_manager','director']`) is what blocks everyone else. Task cancellation lives in the `cancel` **view action**, not inside `transition_to()`, so a plain `transition_to('cancelled', …)` from a shell/fixture/script does only the status change (documented, predictable). The default list-exclude means any new list-consuming surface inherits "cancelled hidden" for free; surfaces that must show cancelled pass `show_cancelled=true`. Approved-quota reconciliation is deliberately **manual** — auto-rejecting approved `QuotaUsageRecord` rows would silently mutate FIFO consumption that analytics/historical reporting depend on. Deferred (see plan): notifying Trip Mgmt (external) when a cancelled shipment had a truck reserved; bulk-cancel; an enum reason code; un-cancel (model as "create a new shipment from this one's data" instead). Tests in `tests_cancel.py` (27) cover per-status cancel, role/empty-reason/terminal rejection, task cancellation, no-auto-advance, quota cleanup, the `allowed_transitions` filtering + `barysh_gumrugi` regression, and the default list-exclude.


## ADR-020: Realtime Stack — Django Channels + Redis + uvicorn workers (one global Sheet presence room)
**Decision**: Introduce a WebSocket layer using **Django Channels 4** with the **`channels-redis`** channel layer (backed by the existing `redis:7-alpine` service). The Django container moves from `gunicorn config.wsgi:application` to `gunicorn -k uvicorn.workers.UvicornWorker config.asgi:application` so a single uvicorn process pool serves both `/api/` HTTP and `/ws/` WebSocket on port 8000. nginx forwards `/ws/` with `Upgrade` + `Connection` headers and a 3600 s read timeout. The browser opens **one socket per tab** at `/ws/app/`; it carries a multiplexed envelope `{channel, type, payload}` so future features (work-time heartbeat, push notifications, cell-cursor sharing) can ride the same connection without a second deployable. Cookie-JWT auth is ported from `apps.core.authentication.CookieJWTAuthentication` to a Channels middleware that reads the `access_token` cookie out of the ASGI handshake scope; anonymous handshakes close with code 4401. Sheet presence is the first channel — group `presence.sheet`, **one global room** (not per-season, not per-filter), with the roster stored in the Redis hash `presence:sheet` (mapping `channel_name → {user_id, name, role, color, joined_at}`) so every uvicorn worker sees the same membership. Tests auto-select `channels.layers.InMemoryChannelLayer` (under `RUNNING_TESTS`) and a module-level dict mirrors the Redis hash so the test path needs no Redis. `daphne` is added as a **test-only** dep (channels.testing eagerly imports it) — production uses uvicorn.

**Context**: Two upcoming features needed the same primitive — a persistent client→server connection: (1) Sheet presence avatars (Google-Sheets-style awareness — the Sheet is the only screen where multiple roles edit overlapping cells within the same hour), and (2) per-user work-time logging. Polling for either would mean ~1 request/user/15 s app-wide and presence-leave detection lagging by the poll interval. The roadmap (`docs/specs/YGT_Digital_Transformation_Roadmap.docx`) already names "Django Channels + WebSocket" as the planned realtime stack, and `docs/obsidian/processes/comments-tasks.md:186` explicitly defers WS as "acceptable to skip for human-pace ops" — this is the trigger to finally introduce it. Alternatives considered: (a) **daphne for everything** — loses gunicorn's worker-pool management; (b) **daphne sidecar on a separate port** — two processes, two ports, more nginx config; (c) **FastAPI sidecar** or **Pusher/Ably** — second deployable / external dep, neither justified at beta scale. Single-uvicorn-under-gunicorn is the Channels docs' own recommended production pattern. Per-season presence rooms were rejected: only one season is active at a time and filtering by it would split rooms artificially. The decision to ship **presence first, work-time later** (rather than both in one plan) came from a scoping question — presence is low-stakes and immediately visible, work-time has data-model + privacy weight that benefits from a separate review.

**Consequences**: Future channels add new dispatch branches in `apps/core/consumers.py:AppConsumer` (and matching `on()` subscriptions in `frontend/src/services/realtime.ts`) — no new sockets per feature. Multi-worker correctness is automatic for any feature that uses the channel layer's `group_send` + a Redis-side state hash; features that try to keep state in process-local memory will silently diverge across uvicorn workers. The `--workers 3` setting is now load-bearing for HTTP throughput AND for WS broadcast fan-out; raising it changes both. nginx's 3600 s `proxy_read_timeout` is intentional headroom for Phase 3 work-time heartbeats — don't shrink it without coordinating. `wsgi.py` is left in place but unused (harmless). Tests use `TransactionTestCase` + `WebsocketCommunicator` driven via `asyncio.run` — see `apps.core.tests.test_app_consumer` (5 cases). Frontend WS client is a **singleton** that lives outside React and survives route changes; React touches it via `useRealtime()` (subscribes status into the Zustand store) and feature hooks like `usePresenceSheet()`. Reconnect uses exponential backoff (1 s → 2 s → … cap 30 s) and only fires while `navigator.onLine === true`; close code 4401 is treated as terminal (user must re-login). Multi-tab same-user is **accepted** as two roster entries — matches Google Docs. Phase 3 work-time logging (the second feature this plumbing was built for) reuses the same socket with channel `worklog.heartbeat`, persists to a new `core.work_sessions` table, and adds a `python manage.py reap_work_sessions` cron job (no in-process timers — they would race across uvicorn workers). Pre-locked decisions for Phase 3: every user can see everyone's hours (radical transparency), "tab open at all" counts as working, `WorkSession.active_seconds` accumulates per-heartbeat capped at `min(now - last_heartbeat_at, 2 × heartbeat_interval)` to neutralise laptop-sleep gaps.


## ADR-021: Non-Shipment Tasks — `Task.kind` + Weekly-Plan To-Dos
**Decision**: Make `Task.shipment` **nullable** and add a `kind` discriminator (`shipment` | `weekly_plan`, default `shipment`) plus three context columns (`link`, `scope_year`, `scope_week`) to `apps/export/models/task.py`. This unblocks the first non-shipment task type: a per-manager **weekly harvest-plan** to-do. Generation is **on-demand** — `POST /api/v1/export/tasks/generate-weekly-plan/` (supervisors only: `PRIVILEGED_ROLES`) creates one `weekly_plan` Task per active `BlockManagerAssignment` user for the given ISO `(year, week)`, idempotently (skips a manager who already has one for that week). The task carries `assignee_user` (the specific manager), `assignee_role='greenhouse_manager'`, `completion_rule=MANUAL_DONE`, and `link='/export/plan?week=…&year=…'`. Generation + resolution live in `apps/export/services/weekly_plan_tasks.py` (export reads greenhouse `BlockManagerAssignment` / `HarvestDayEntry` — the allowed dependency direction). Auto-completion is **lazy**: `MeTaskListView` (`/me/tasks/`) calls `resolve_weekly_plan_tasks_for_user()` on read, marking the task DONE once **no blank plan cells remain** for the manager's blocks that week (every assigned block has ≥1 `HarvestDayEntry` row and none has `plan_value IS NULL`; an explicit `0` counts as filled). A `resolve_weekly_plan_tasks` management command does the same across all users for cron/backfill. `/me/tasks/` non-supervisor scoping is tightened from "role only" to `assignee_role==role AND (assignee_user IS NULL OR assignee_user==me)` so personal weekly tasks stay private while role-wide shipment tasks (null `assignee_user`) remain visible. The existing P1/P2/P3 dispatcher plan-reminder **notifications** are kept — the task is additive, not a replacement.

**Context**: Greenhouse managers must fill the weekly harvest-plan grid (`HarvestDayEntry.plan_value`), but the only prompt was the dispatcher's ephemeral notifications — there was no durable to-do on their board. The `Task` model was strictly shipment-bound (non-nullable FK), so this had been deferred as "needs `Task.shipment` nullable". The user asked for a real board task, click-to-navigate to the plan page, that auto-completes when the week is fully entered.

**Consequences**: `Task.shipment` being nullable means every consumer must null-guard — `TaskListSerializer.get_phase` already did; frontend consumers (`SelfKanbanCard`, `SelfBoardTaskDrawer`, `OtherTasksRow`, etc.) gained guards and `ITaskListItem.shipment` is now `number | null`. Resolution is lazy because greenhouse (upstream) may not call into export — the plan-save path (`set_plan_value`) cannot trigger export-task logic; worst case the card flips DONE on the next `/me/tasks/` load (the nav badge polls every 60 s). If instant-on-save is ever required it needs an export-side hook, not a greenhouse import. "No blank cells" is judged only against `HarvestDayEntry` rows that exist for the week, so it relies on the grid's `initialize-week` having created the day rows; requiring ≥1 row per assigned block guards against a premature done. The new `kind` opens the door to further non-shipment task types (e.g. local-sell-plan, truck-allocation reminders) on the same board plumbing. Tests in `apps/export/tests_weekly_plan_tasks.py` (9) cover generation idempotency, inactive-assignment exclusion, blank-cell/zero/no-rows resolution, endpoint auth, and `/me/tasks/` manager isolation.


## ADR-022: Delegated user management for department heads
**Decision**: A bounded carve-out of AD-15's admin-only user/permission administration: the `loading_dept_head` role may **create / edit / delete / reset-password** users, but ONLY for the `loading_dept_head_deputy` and `weight_master` roles, and may **grant those two roles a subset of his own visible pages**. The who-may-manage-whom map is a hardcoded single source of truth — `MANAGEABLE_BY_ROLE = {'loading_dept_head': {'loading_dept_head_deputy', 'weight_master'}}` in `apps/core/roles.py`, with helpers `manageable_roles(user)` (admins/superusers → every role) and `can_manage_users(user)`. The head's **deputy does NOT inherit this power** — only the head manages staff (scope decision). Enforcement is entirely server-side in `UserManagementViewSet`: `get_queryset` scopes a delegated manager's list to his manageable roles; `create`/`partial_update` validate the assigned role via `_assert_can_assign_role` (the *new* role must be in the set, blocking escalation to `admin`); `partial_update`/`destroy`/`set_password` validate the target's *current* role via `_assert_can_manage`. Page delegation is a **separate, scoped endpoint** — `GET/PUT /api/v1/export/admin/managed-page-permissions/` (`ManagedPagePermissionsView`) — NOT the admin full-matrix PUT (which stays `_AdminOnlyPermission` and delete-all). The PUT is a **surgical `update_or_create`** over only the `(managed_role, grantable_page)` pairs in the payload; rows for other roles or other pages are never touched. "Grantable" = pages the manager's own role can currently see, **excluding every `admin.*` page** (privilege-leak guard — the head sees `admin.users`/`admin.staff_access` to use the feature but cannot re-grant them). A data migration (`core.0020`) sets `admin.users` + the new `admin.staff_access` page visible for `loading_dept_head` so the feature is reachable.

**Context**: The user (system administrator) wanted the loading department head to run his own corner of the org — onboard and manage his deputy and weightmasters without waking the admin for every password reset or new hire — while staying strictly inside the slice of the app he himself can see. AD-15 had centralised ALL user + permission administration on the `admin` role; this is the first deliberate delegation of a piece of it. Page permissions are stored per-**role** (not per-user), so a grant to `weight_master` is role-wide — acceptable and made explicit in the UI copy, since the managed roles map 1:1 to the head's small team.

**Consequences**: AD-15's rule "only permission-matrix / user-management endpoints belong behind `_ADMIN_ONLY`" still holds for the matrix CRUD; this ADR is the documented exception for a *scoped* slice of user management. Future contributors extending delegation must add to `MANAGEABLE_BY_ROLE` and rely on the same two guards (`_assert_can_manage` for the target's current role, `_assert_can_assign_role` for the assigned role) — never widen `get_queryset` without re-checking both. The admin-page exclusion in `ManagedPagePermissionsView._grantable_pages` is load-bearing: dropping it would let a head hand subordinates entry into user/permission administration (the action gates would still 403, but the pages would leak). The new `admin.staff_access` page_code is registered in `permission_registry.py`. The frontend mirrors `MANAGEABLE_BY_ROLE` only for UX (which dropdown options / action buttons to render) — it is not a security boundary. Tests in `apps/export/tests_delegated_user_mgmt.py` (18) cover list scoping, create/patch/delete/set-password bounds, escalation-to-admin rejection, the surgical upsert (an out-of-band admin grant survives a head PUT), and admin-page / unmanaged-role / ungrantable-page rejection.


## ADR-023: A "2-Sales" row is a FirmSplit, not a truck — Shipment→FirmSplit→Contract + bridge invariant

**Decision**: One row of the Excel `2-Sales` sheet represents **one export firm's share of a truck** (a *firm split*), **NOT** a whole truck/shipment. The canonical domain hierarchy is three levels: `Shipment (one physical truck) 1──< FirmSplit (1-3, one export firm's share) ──> Contract`. A FirmSplit is the unit that produces one Invoice + one CMR (documents are *generated outputs*, never data tables — a row is never called an "invoice"). One physical truck is commonly split across **2 firms (~35.6%)**, rarely 3, to keep each invoice under the **$10,000** threshold (<$10K settled in cash, >$10K through the bank). Two **distinct identifiers** must never be conflated: `shipment_code` = `DDMM+seq/YY` (e.g. `02FB005/26`, generated by the warehouse at loading, exactly one per truck) versus `contract_no` = `{seq}/{YY}-{FIRM}-EXP` (e.g. `6/26-YGT-EXP`, 1-3 per truck, where `seq` is a running counter **per export firm per year**). The **bridge invariant** between the two app modules is the identity key **`(shipment, export_firm)`**: `export.ShipmentFirmSplit` (export-lifecycle side) and `contracts.ContractSale` (contracts/financial side, the 2-Sales row) describe the same firm-share and are joined on that pair.

**Context**: The original `ContractSale` model and the `import_invoices_from_2sales` command were framed as "one row = one truck dispatched" (the model docstring literally said so). The user confirmed against real data that this framing double-counts trucks and breaks contract/weight reconciliation: 1075 row-pairs share the same truck number but differ in seller firm + invoice + contract (e.g. truck `4248AHF/2419TAH` → YGT inv 294 contract `178/25-YGT-EXP` **and** HMS inv 283 contract `169/25-HMS-EXP`). The platform currently carries **two overlapping firm-share models** — `export.ShipmentFirmSplit` (no contract link) and `contracts.ContractSale` (contract link + a nullable `shipment` FK that nothing populates) — and the 2-Sales importer writes one `ContractSale` per row without reconstructing the truck. This ADR records the agreed conceptual model and the bridge invariant as the **target** before any code/data migration.

**Consequences**: This ADR is **documentation only** (Slice 0 of the agreed plan) — it changes no schema, behaviour, or data. It fixes the misleading "one truck" wording in `contracts/models/contract_sale.py`, `export/models/shipment.py::ShipmentFirmSplit`, and the `import_invoices_from_2sales` docstring, and establishes `(shipment, export_firm)` as the canonical bridge key for the **chosen architecture path = B (bridge the two models, do not merge)**. The remaining slices are deferred and tracked separately: Slice 1 — contract auto-numbering (`seq`/`year` ints + unique index `(export_firm, year, seq)`, `next_contract_no()` service); Slice 2 — `Contract.kind` (`framework`/`one_time`) and move `passport_sdelka` onto `Contract`; Slice 3 — rework the 2-Sales import to group rows by `(truck_plate + date)` into `export.Shipment`, create `ShipmentFirmSplit` per row, and populate `ContractSale.shipment` (the bridge); Slice 4 — the "Add shipment" flow creates one `Shipment` + N `FirmSplit`, each with its own generated `contract_no` and a $10K non-blocking warning; Slice 5 — verify Invoice/CMR generate one-per-FirmSplit. Open decisions still pending before Slice 3: owner of weight/amount truth (`ShipmentFirmSplit` vs `ContractSale`), and how already-imported `ContractSale` rows get back-linked to shipments. See memory note "2-Sales Firm-Split Model".


## AD-16: Season lifecycle — close, open, browse read-only

**Decision**: `core.Season` gains a real lifecycle. Two new columns — `closed_at` (nullable datetime) and `closed_by` (nullable FK to `User`, `PROTECT`) — plus a **filtered unique index** (`uq_season_single_active`, `condition=Q(is_active=True)`) enforcing that at most one row has `is_active=True`. State is **derived, never stored**: `UPCOMING` (`closed_at IS NULL`, `is_active=False`), `ACTIVE` (`is_active=True`), `CLOSED` (`closed_at IS NOT NULL`) — exposed as a read-only `status` property, never a persisted column. `Season.is_active`, which historically did two unrelated jobs, is split into two functions in a single new module, `apps/core/seasons.py`: `get_active_season()` is the **write target** (deterministic — the unique index guarantees at most one row, no tie-break needed) and `resolve_season(request)` is the **per-request read scope** (`?season=<id>`, falling back to the active season). A `SeasonScopedMixin` applies `resolve_season()` to a viewset's queryset via `apply_season_scope()`; hand-written `.filter(season_id=...)` per viewset was rejected — with ~20 endpoints to convert, the one a future contributor forgets silently leaks closed-season data, which is exactly what this feature exists to prevent. When `resolve_season()` finds no active season at all (the legitimate gap between closing one season and opening the next), `apply_season_scope()` returns `qs.none()`, never the unfiltered queryset (**D7 — fail closed**, added after implementation review found the naive "no filter" answer fails *open*: every closed season's data would become visible to every user, regardless of the `closed_season` permission, in exactly the window an admin creates deliberately at end of season; detail routes are unaffected — they bypass season scoping entirely by design, so a direct link still resolves during the gap). Two lifecycle services, `close_season()` and `open_season()` (`apps/core/services/season.py`), do the actual state change: `close_season()` sets `closed_at`/`closed_by` and clears `is_active` — **it does not touch any shipment, plan, or contract row** (D2) — while `open_season()` atomically deactivates the incumbent and activates the target inside one transaction, so the unique index is never transiently violated. Reopening a closed season is **deliberately unsupported**: `open_season()` raises `ValueError` (→ 409) if the target is already closed, and `Season.assert_activation_allowed()` (called from an overridden `Season.save()`) blocks `is_active=True` from being set on any row that already has `closed_at` set, covering the ORM, Django admin and management-command paths. The API path is closed differently, and its shape changed twice. `is_active` was writable at first, which produced three distinct failures: every `POST /admin/seasons/` carrying `is_active=True` 400'd while another season held the flag (the admin form defaulted the switch on, so creating a season was simply broken); toggling Active through the generic PATCH left the whole client on stale season state, because `useUpdateSeason` invalidated only `['admin-seasons']` while `useOpenSeason`/`useCloseSeason` invalidate everything including `/auth/me/`; and it bypassed `open_season()`/`close_season()` entirely, so there was no atomic incumbent swap and no `AuditLog` row. The 2026-08-07 cleanup made the field a `read_only_field` and deleted the Active switch, which removed all three by removing the capability. **The domain owner asked for the switch back, and it was restored 2026-08-10 with the write DELEGATED rather than performed** (`SeasonViewSet.perform_create()` / `perform_update()`): `perform_create()` always INSERTs the row inactive and then calls `open_season()` if `is_active=True` was sent, so the uniqueness constraint has nothing to collide with and the incumbent swap is still the services' single atomic transaction; `perform_update()` pops the flag out of `validated_data` so `ModelSerializer.update()` never writes it, routing `False -> True` to `open_season()` and `True -> False` to a new `deactivate_season()`. That third service exists so `is_active` keeps exactly one writer and the stand-down is audited too: it clears the flag WITHOUT closing (`closed_at` stays NULL, the season returns to UPCOMING and can be opened again), leaving the platform with no active season — the legitimate gap D7 already fails closed on. The seam is the viewset, not the serializer, because a view calling a service is the sanctioned shape here (`views` must not *contain* business logic; `TruckSplitDefaultViewSet` in the same file already uses `perform_*` this way) and `SeasonSerializer` has no consumer outside `SeasonViewSet`. Frontend counterpart, without which defect 2 returns immediately: `useCreateSeason` AND `useUpdateSeason` now run the same blanket `queryClient.invalidateQueries()` as the lifecycle mutations — create is included because ticking Active on the create form also moves the write target. The form defaults the switch **off**, deliberately and not merely because defaulting it on used to 400: adding next year's season is bookkeeping, and silently moving the platform-wide write target is not a side effect a create form should have. **A correction to what the 2026-08-07 entry claimed, since it would mislead the next person to touch this:** the validator that 400'd the create is a *field-level* `UniqueValidator` DRF 3.17 attaches to `is_active` (its queryset is already `Season.objects.filter(is_active=True)`), NOT a serializer-level `UniqueTogetherValidator` — `SeasonSerializer.validators` is `[]` even with the field writable, so `Meta.validators = []` and overriding `get_unique_together_validators()` are both no-ops against it (verified by inspecting `serializer.fields['is_active'].validators`). Making the field read-only worked because read-only fields get no validators attached at all. Declaring the field explicitly (`is_active = serializers.BooleanField(required=False)`) is what removes it now, and is load-bearing: collapse that declaration back into `Meta.fields` and every season-switching write 400s again. `SeasonSerializer.validate_is_active()` came back with the writable field (it had been deleted 2026-08-07 as unreachable, correctly: DRF never calls `validate_<field>` for a field absent from `to_internal_value`). It reuses `Season.assert_activation_allowed()` so the predicate cannot drift, and it exists because both alternatives surface as a raw 500 rather than a 400 — `open_season()`'s `ValueError` is not caught by the generic `update()`, and the model guard's `django.core.exceptions.ValidationError` is not translated by the custom exception handler. With it in place `open_season()`'s own refusal is unreachable from the API except in a TOCTOU window (a season closed between `is_valid()` and `perform_update()`); that residual 500 is accepted rather than padded against. Consequence on the wire, twice reversed: `PATCH {"is_active": true}` on a closed season returned **400**, then **200 having changed nothing** (2026-08-07), and is a **400 keyed on `is_active`** again (2026-08-10). Reopening a closed season remains unsupported at every layer. A `close_preview()` service returns advisory counts (`drafts`, `in_transit`, `open_tasks`, `unfinished_plans`, and — since 2026-08-08 — `draft_quota_usage`) for the admin confirm dialog — the only mitigation for the fact that closing hides unfinished work rather than blocking on it. The fifth key exists because the other four all describe work that is *hidden* and returns read-only, while a `QuotaUsageRecord` still in `draft` becomes **permanently unapprovable** once its season freezes (approving is a write to frozen data; there is no unfreeze) — a consequence the close itself creates and the dialog was silent about. It is counted through `usage_season_q()` so no second season-ownership rule enters the codebase, and the modal renders it as a separate warning rather than folding it into body copy that promises "nothing is deleted". The original four keys are a contract the frontend interpolates by name: adding a key is safe, renaming or removing one is not. `closed_season` is a new `RESOURCE_REGISTRY` entry (`apps/core/permission_registry.py`), not a new action on the existing `season` resource — `RoleResourcePermission`'s action vocabulary (`can_view`/`can_create`/`can_edit`/`can_delete`) has no room for "may browse a closed season" without a schema change, so it becomes its own resource where only `can_view` is ever seeded (create/edit/delete are meaningless for it — closed seasons are read-only by design), granted to `admin`, `director`, `boss`, `export_manager`, `finansist` (matching `_ARCHIVE_VIEW_ROLES` in `apps/export/views.py`) but admin-editable afterwards with no code change. ADR-0005 already hides rows by default via the `is_archived` operational/archive split; inside a **closed** season, archived rows are returned **only if the user is ALSO in `_ARCHIVE_VIEW_ROLES`** — everyone else sees a partial (non-archived-only) view, disclosed in the frontend banner rather than hidden (**D8**, reversed mid-implementation from the original design, which bypassed the archive split unconditionally for anyone holding `closed_season.can_view` — review found that made the permission a silent superset of archive-view access, which would hand archived rows, including historical buyer prices, to a role nobody decided should have them the moment an admin granted `closed_season` to a sixth role; a partial view is a UI problem, the original rule was a security problem). `QuotaIssuance` gained a `season` FK for the write freeze (**D10**, ruled after Task 9's review found issuances stayed editable after a close), and that FK now drives the read scope too: **D11** (ruled 2026-08-06 during user testing) reverses D10's read-scoping exemption and holds that **quota never crosses a season boundary, in either direction** — `QuotaIssuanceViewSet` is season-scoped like any other direct-FK endpoint, and FIFO consumption stops at the boundary, so `compute_fifo_usage(product_type, season)` and `compute_firm_quota_balances(product_type, season)` take the season explicitly and a shipment can only draw on its own season's quota, with leftover issuance expiring rather than carrying forward. Three structural facts made this more than a filter change. (1) `QuotaUsageRecord` has **no** `season` FK and **no** `issuance` FK — only `usage_date` and a nullable `shipment`, and 575 of its 711 rows on the live database have no shipment at all — so its season is *derived* by `services_quota.usage_season_q(season)`: `shipment.season` when linked (authoritative even when `usage_date` falls outside that season's calendar range, which is real for 7 rows), else `usage_date` inside the season's range. A stored FK was considered and rejected: it would be the more auditable anchor, but `freeze_season_of()` reads `obj.season` **before** `obj.shipment.season`, so any creation site that failed to stamp it would silently read a closed-season row as open — loosening the very freeze D10 added. (2) `SeasonScopedMixin.include_null_link` cannot express that rule (it means "visible in *every* open season", which D11 forbids) and cannot be used with a direct `season` FK at all (there is no separate anchor column to test), so `QuotaUsageViewSet` overrides `apply_season_scope()` with the same predicate FIFO uses — display and consumption share one definition on purpose, so the grid can never show a row the ledger does not count. (3) Both quota cache keys (`fifo_usage:*`, `quota_firm_balances:*`) are now parameterised by season id, and `invalidate_quota_caches()` enumerates the seasons to bust them, since Django's default backend has no pattern-delete. Because the usage anchor is *derived* rather than stored, the write paths must enforce what the read predicate assumes: `POST`/`PATCH` on `/quota-usage/` reject a row that would belong to no season (`season_of_usage()` is the row-level inverse of `usage_season_q()`, and the two must stay in step), and the usage grid's month picker disables months lying outside every season. Without that guard D11 *created* a new failure mode — before it, `include_null_link` surfaced an unlinked row under the active season whatever its date; after it, an unlinked row dated in the inter-season gap matches no season and vanishes the instant it saves. **The same derivation had to be pushed into the write freeze as well, and was not until 2026-08-08** (found by an automated reviewer, the eighth closed-season hole of the branch and the first not found by a human-directed sweep): `freeze_season_of()` reads `obj.season` then `obj.shipment.season`, and an unlinked `QuotaUsageRecord` has neither, so it resolved to `None` — which `assert_season_open()` treats as *open*. Both layers were therefore silent no-ops on exactly the 575 unlinked rows: `POST` of a usage row dated inside a **closed** season returned 201, a `PATCH` moving one into a closed season returned 200, and `DELETE` of one returned 204, each mutating a balance the freeze exists to hold. The fix is a `freeze_season` property on `QuotaUsageRecord` — the third such hook after `ContractSale` (nullable `shipment`, authoritative `contract`) and `FinansistAdvance` (junction-derived) — delegating to `season_of_usage()` rather than repeating the date-range lookup, so the row a closed season *lists* is the row it *freezes*; the import is deferred inside the property because `services_quota` imports the models package at load time (a module-level import raises `ImportError`, verified). The bulk `approve` action needed its own correction for the same reason: `assert_bulk_seasons_open(qs, 'shipment__season')` resolves through a NULL FK for those rows and matched no season, so approving a closed season's unlinked drafts was permitted even though it never touches `usage_date` or `shipment` — it is now `services_quota.assert_usage_batch_seasons_open()`, which applies `usage_season_q()` once per closed season and subsumes the generic call. Deliberate status-code split, since both failures are reachable from the same POST: a row that resolves to **no** season is a **400** on the `usage_date` field, a row that resolves to a **closed** season is the branch's **409 `season_closed`**. One wire-level consequence on the dominant row shape, stated rather than buried (the same class of change as the `PATCH {"is_active": true}` 400→200 note above): 560 of the 575 unlinked rows are `status='approved'`, and `perform_update`/`perform_destroy` reject a non-draft row with `400 Only draft records can be edited/deleted` — layer 1 now fires *before* those bodies, so `PATCH`/`DELETE` on an approved unlinked row inside a **closed** season returns **409 where it used to return 400**. Outside a closed season the draft-only 400 is untouched, and both are pinned by tests. Operational consequence, disclosed rather than mitigated: on the dev database 15 of the 575 unlinked rows are still `status='draft'`, and once their season closes they can never be approved (there is no unfreeze) — they should be approved or deleted before the close, alongside the straddling-advance check. Relatedly, `used_kg` on the issuance **detail** route is keyed off the row's own `season`, not the request's: detail bypasses season scoping by design (Rule A), so resolving the request's season there reported `used_kg: 0.00` for every issuance outside the active season. Accepted, disclosed consequence: an issuance whose `issue_date` falls in the gap between two seasons carries `season = NULL` and is invisible on every list — `QuotaIssuance#34` on the dev database (25,000 kg, 2026-07-06, firm *Eziz Doganlar*) is exactly that row, left for the owner to rule on rather than guessed at; `POST /quota-issuances/` now 400s during the close→open gap so no further ones can be created. Measured impact on the live dev database: consumption totals for the season that holds the data are **unchanged** (19,771,100 kg tomato / 144,000 kg pepper before and after) and **no firm's balance moves** — the only ledger difference is that issuance #34's allocation drops out, and it was already consuming 0 kg. **Amended 2026-08-10 — the quota-usage approval step is gone, which retires several sentences above.** The domain owner ruled that usage must count automatically. Rows are now created `status='approved'` by both `QuotaUsageViewSet.perform_create` and `quota_sync.sync_draft_quota_usage_for_shipment`; `POST /quota-usage/approve/` is deleted; and `perform_update` / `perform_destroy` no longer gate on `status`, so `400 Only draft records can be edited/deleted` no longer exists — which retires the wire-level 400→409 note recorded above for the dominant unlinked-row shape, since there is no 400 left to be superseded (the 409s themselves are unchanged and still tested). `assert_usage_batch_seasons_open()` survives in `services_quota` for any future bulk action but has no caller. `approved_by` / `approved_at` stay **NULL** on everything the system creates: `'approved'` means "counted", not "signed", and stamping the acting operator would put a false signature in the audit trail. The column is kept rather than migrated away so pre-cutover history stays readable. **The change is not the one-line status flip it looks like**, because `sync_draft_quota_usage_for_shipment` refused to run (`ApprovedQuotaExistsError` → 400) whenever approved rows existed on the shipment — a guard whose whole premise was that approved meant a human signature. Once every row is born approved it fires on *every* firm-split edit after the first, so it would have 400'd routine work across the platform; three call sites carried it (`ShipmentViewSet.set_firm_splits` and two in `contracts.views`) and all three are removed, with resync now replacing every row on the shipment. Manually-entered rows carry no shipment and are never in that queryset. The operational disclosure recorded above — that draft rows become permanently unapprovable once their season closes — is resolved rather than mitigated: no new draft can be created, and `approve_legacy_quota_usage` converts the pre-cutover ones (151 rows / 1,732,452 kg on the dev database, +9% on that season's consumption). `close_preview()`'s `draft_quota_usage` counter is therefore structurally 0 and is kept only as a backstop for an environment where the backfill has not run. Two consequences left standing rather than papered over: `POST /shipments/{id}/cancel/` still reports `draft_quota_deleted` (now always 0) and `approved_quota_to_reconcile` (now every row on the shipment) — no kg is stranded, since `counted()` already drops rows tied to a cancelled shipment, but the field names read oddly; and **whether a `is_gapy_satys` shipment should consume quota at all is an open question** referred to the business (3 shipments / 4 rows / 36,000 kg on the dev database, all to Kyrgyzstan). Until it is answered gapy shipments consume quota exactly like any other, which is the pre-existing behaviour, not a new decision. The write freeze itself is two layers, because not every write path goes through DRF object permissions: `SeasonNotClosed` (a DRF object permission, `apps/core/permissions.py`) is layer 1, and `assert_season_open()` / `assert_bulk_seasons_open()` / `assert_season_id_open()` (`apps/core/seasons.py`) called from services, `transition_to()`, the Sheet bulk-edit, the two-row Join, and every `perform_create`/`perform_update` on a scoped viewset are layer 2 — the layer that actually holds the invariant, since layer 1 cannot fire on a POST-to-collection (`CreateModelMixin.create()` never calls `get_object()`) or on the bulk/body-id write paths. Both layers raise `SeasonClosedError`, mapped to `409 {"error": "season_closed", "season": "<name>", "closed_at": "<iso>"}` — 409, not 403, because the request is well-formed and the user is authorised in principle; it conflicts with the resource's state, which is how the frontend needs to treat it (a banner, not a permission error).

**Context**: `Season.is_active` existed as little more than a label doing two unrelated jobs — the write target for new shipments, and an ad-hoc read filter copy-pasted (with inconsistent tie-breaks) across at least nine call sites. There was no way to close a season, no way to open the next one atomically, and no way to look back at a previous season's data — closed-season rows stayed mixed into every board, list, and dashboard forever. The user needed: close a season (its data freezes and disappears from default views), open the next one, and let permitted users browse a closed season read-only. D7 and D8 above were not part of the original design — both were added mid-implementation after review found real gaps (design spec `docs/superpowers/specs/2026-08-03-season-lifecycle-design.md`, §3.1 and §9.1 record the before/after). A `status` CharField alongside `is_active` was considered and rejected — two columns encoding overlapping state means a row can contradict itself (`status='CLOSED'` with `is_active=True`), and deriving state from `is_active` + `closed_at` makes that contradiction unrepresentable. Reusing `is_archived` as the close mechanism was also considered and rejected: several season-bearing models (`WeeklyHarvestPlan`, `HarvestDayEntry`, `TruckAllocation`, `Contract`) have no `is_archived` column, and `?archived=true` cannot distinguish *which* closed season is being viewed, which is the actual request.

**Consequences**: Future contributors adding a season-bearing model or a new list endpoint must use `SeasonScopedMixin` + `season_field` rather than a hand-written filter — the design spec's §4 endpoint classification table is the checklist, and an endpoint absent from it is a bug. **That checklist was built from the router registrations, so it missed the endpoints that are plain `APIView`s** — `/me/tasks/` (`MeTaskListView`, `apps/core/views_me.py`) shipped unscoped even though `TaskViewSet` was scoped, and since the My Tasks screen lists from `/me/tasks/` and never from the viewset, the season switcher had no effect on that screen at all (spec §4.8, fixed 2026-08-06). The mixin's predicate now lives in a standalone `season_scope_q(season, season_field, include_null_link)` in `apps/core/seasons.py` precisely so a non-viewset can apply the identical rule instead of a hand-rolled filter that drifts from its viewset twin. When auditing scope coverage, enumerate `APIView` subclasses too, not just `router.register` calls — **and plain `viewsets.ViewSet` subclasses, which are the same structural category**: a 2026-08-07 review found `KpiViewSet` (`views_kpi.py`) missing from an otherwise-complete sweep table. It is named in the design spec's §4.3 but was never converted: its four actions use rolling 7/30-day windows rather than a season range, and `kpi_blocked_age()` has no window at all, so a closed season's still-blocked tasks (D2 leaves them blocked) contribute to its aggregate. It exposes counts and durations only — no season-identifiable row — and has no frontend consumer, so it is recorded rather than changed, pending the owner's own KPI testing. A nullable season FK (`Contract.season`, `WeeklyLocalSellPlan.season`) must stay nullable — a strict `filter(season=X)` silently drops NULL rows, so `SeasonScopedMixin.include_null_link=True` OR-in `IS NULL` when the resolved season is open (closed-season browsing hides unlinked rows, since an unlinked row belongs to no season and has no place in a specific season's archive). `boss` cross-season analytics is the one deliberate exception to scoping-by-default: the resolved season **parameterises** the comparison (`current_season` vs `previous_season`) rather than filtering it, because scoping it would empty `previous_season` and silently break every comparison chart — but this only applies to `revenue()`; every other `boss/*` action ignores `?season=` and reads `get_active_season()` via `?period=` instead, while `dashboard/summary` and `team-kpi?period=season` do follow the resolved season — and both now also fail closed during the close→open gap (final-review finding F3): `dashboard/summary` returns an all-zero/empty payload with the response shape preserved instead of substituting a current-month range that, since seasons run Sept→Aug, still covered the just-closed season; `quota-dashboard` (the sixth and last instance of the same shape — a read path that built its own queryset instead of going through `resolve_season()`, after `block_summary`, the customs `/ledger/`, the `?shipment=` pin, contract-sale via `contract`, and advance-create) now resolves through `resolve_season()` too, so `closed_season.can_view` is finally enforced on it, `?season=` became optional with the active season as the default, an unknown id returns 404 rather than 400, and the gap returns the empty-but-shaped payload. **On that endpoint the resolved season also CLAMPS `?date_from=`/`?date_to=` rather than merely defaulting them, and that distinction is the general lesson for every date-windowed endpoint:** `build_quota_dashboard()` aggregates on dates alone, so a caller could send the closed season's own range with no `?season=` at all, pass the gate on the active season, and receive the closed season's numbers — the exact payload the 403 withholds. `max(from, season.start_date)` / `min(to, season.end_date)` is monotonically restrictive, changes no in-season number, and inverts to an empty range for a window wholly outside the season (fail closed); it is what makes it safe to leave the aggregates date-driven, since pushing the season FK into `build_quota_dashboard()` would change published numbers rather than visibility and needs its own ruling; and a **seventh** instance was found by the sweep that fix prompted and closed with it — `GET /harvest-forecast/remaining/` filtered `HarvestDayEntry` on `entry_date` alone, and since that model's `season` FK is non-null and seasons never overlap, a date inside a closed season was a closed-season read available to any authenticated user with no `?season=` for a permission check to hang off (`block-summary` verbatim); the two write validators sharing that service keep no season predicate on purpose, since scoping them would change what a create is validated against rather than gate a read; `team-kpi?period=season` returns `results: []` instead of an unbounded all-time window. Both paths were wired before D7 existed and were never measured against it; blanking the dashboard also zeroes its LIVE `in_transit`/`selling`/`active_shipments` counters for the duration of the gap, which is the accepted cost of "return empty rather than a substitute range". On `team-kpi`, following the resolved season is itself partial: `overdue_now` (`timezone.now()`-based) and `trend` (a fixed rolling 14 days from today) are window-independent, so browsing a closed season returns one row blending that season's completion numbers with *today's* overdue count and a *current* 14-day trend — two epochs in one row, undecided whether to blank, relabel, or accept and document further. Known, honestly-disclosed gaps this branch leaves open, none of which block the feature: a queryset-level `Season.objects.filter(...).update(is_active=True)` bypasses `Model.save()` and therefore `assert_activation_allowed()` entirely — Django's `QuerySet.update()` never calls `save()` — so it can still reactivate a closed season or create a second active one (the DB's `uq_season_single_active` catches only the latter); the branch's own tests use exactly that form to arrange fixtures, which is fine, but it is now the *only* remaining API-reachable-adjacent hole since `is_active` left the serializer, and any future management command must use `.save()`; comment creation on the Shipment Detail page is not season-gated on the frontend (the global 409 toast is its only backstop — every other Detail control was gated explicitly); the live dev database has permission drift predating this feature but newly consequential — `boss`'s `season` row shows full CRUD where `seed_permissions`'s blanket `_VIEW` intends read-only, so `boss` can currently close/open seasons on that database, and `loading_dept_head`/`loading_dept_head_deputy` carry stray all-False `season` rows that neither role's seed entry would create (`seed_permissions` only `get_or_create`s, never overwrites, so neither drift self-heals on a re-seed); and `seed_data.py`'s `update_or_create` on the seed season will raise an unhandled `ValidationError` if it is ever re-run after that season has been closed (fail-loud, not silent corruption, but state-dependent rather than the "structurally impossible" the implementer originally reported). One product question was raised during implementation and never ruled on before this branch shipped: whether a user browsing a **closed** season should see `views_clients_report.py`'s Clients Report for that season — left as an open question, not a decision, and worth a ruling before anyone relies on that report's behaviour for a closed season.
