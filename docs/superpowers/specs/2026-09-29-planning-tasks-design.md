## Решения владельца (2026-09-29)

| Вопрос | Ответ |
|---|---|
| Недельный цикл | Все плановые задачи делаются на неделю **N+1**. Пт N — план теплиц; Сб N — распределение машин (как сейчас); затем транспорт |
| Ревью «план изменили после распределения» | Создаётся, **только если изменилось число машин** за какой-то день. Закрывается кнопкой **«Tanyşdym»** |
| Где транспорт смотрит распределение | **Новая страница транспорта** |
| Что на этой странице сейчас | **Минимум**: распределение N+1 только для чтения, подсветка изменений с прошлого «Tanyşdym», кнопка «Tanyşdym». План конкретных машин и водителей — отдельный подпроект позже |
| Когда ежедневная задача выполнена | Есть хотя бы одна запись **с датой = сегодня**. Открыли вчера на сегодня — тоже засчитано |
| Срок ежедневной задачи | До **конца дня**, потом красная |
| Невыполненная вчерашняя | Утром закрывается сама со статусом «пропущена» |

## Уточнения к тому, что было сказано в чате

1. **Базой для ревью не может быть `total_planned_kg`.** Это поле присылает фронтенд, и импорт Excel тоже его заполняет. Поэтому база — собственный снимок сервера (см. §3).
2. **Округление.** В вопросе про ревью было написано «округление вверх». Код везде считает **по правилам округления**: 1,5 → 2, 1,4 → 1 (`_trucks_for_kg`, `ROUND_HALF_UP`, как `Math.round` во фронтенде). Для ревью берём ту же функцию, чтобы «нужно машин» совпадало с экраном распределения.
3. **«Пропущена» и KPI.** KPI (`services_team_kpi.py`) отменённые задачи не считает. «Пропущена» будет видна в истории задач, но **не в KPI**. Показывать пропуски в KPI — отдельная задача, если нужно.

## Допущения: владелец не отвечал, поправьте, если неверно

- A-1. Число машин сравнивается **по каждому дню** Пн–Сб, а не суммой за неделю.
- A-2. «Распределение заполнено полностью» — критерий **как сейчас**: у каждого дня, где по плану нужна ≥ 1 машина, есть ≥ 1 машина. Точного совпадения с потребностью не требуем.
- A-3. У транспортной задачи срок — **конец дня создания**.
- A-4. Ревью (п. 2b) и повторные транспортные задачи возникают только **до конца недели N+1** (до субботы). Прошедшие недели не трогаем.
- A-5. Сетка плана по-прежнему создаётся каждый день в 06:00. На пятницу переезжает только **создание задачи**.
- A-6. Задачи создаются только в активном сезоне, как и сейчас.

## 3. Снимки для «Tanyşdym»

Снимок — строка вида `"1:3;2:4;…"` (для ревью: день → нужно машин) или `"1:5:2;…"` (для транспорта: день:направление:машин). Хранится в новом поле `Task.ack_snapshot` (`TextField`, только ASCII, поэтому collation не нужен).

Где лежит база для сравнения:
- **Ревью 2b** — на задаче `truck_allocation` этой недели (она одна на неделю). Её `ack_snapshot` переписывают создание задачи, каждый `set_splits` и каждое «Tanyşdym» по ревью.
- **Транспорт 3** — снимок **последней закрытой** задачи `transport_plan` за эту неделю.

Если база пустая (старая задача, созданная до этой функции), первый запуск синхронизации просто записывает базу и ревью не создаёт.

**Уточнения после финального ревью (2026-09-29):**
- Пустая база записывается как `";"`, а не `""`. `""` означает «базы ещё нет», и такую задачу синхронизация принимает молча. Без этого различия рост плана после пустого плана прошёл бы без ревью.
- «Tanyşdym» нажимают роль исполнителя, а также admin, boss и director (решение владельца 2026-09-29). Export manager, который сам вносит изменения, не может закрыть ревью транспорта.
- Клиент отправляет снимок, который видел. Если данные с тех пор изменились, сервер отвечает 409, и страница перезагружается.

**Имена видов задач** в коде: `alloc_review`, `transport_plan`, `daily_loading`, `daily_export`. Колонка `Task.kind` — `max_length=16` с индексом. Менять длину индексированной колонки на MSSQL рискованно, поэтому имена укорочены.

**Когда делается снимок.** Только в синхронной точке записи, никогда не внутри ленивого закрытия:
- **Ревью 2b.** Снимок — при создании задачи 2 и в каждом `set_splits` при сохранении распределения (это код `export`, импорт разрешён). Он пишется в задачу 2. Следующие — при нажатии «Tanyşdym». Если снимать при ленивом закрытии, правка плана между сохранением распределения и следующим чтением `/me/tasks` попала бы в базу, и ревью не возникло бы никогда.
- **Транспорт 3.** Снимок — при нажатии «Tanyşdym».

**Защита от дублей.** Лениво (при чтении `/me/tasks/`) задачи только **закрываются и отменяются**. **Создаются** они только в beat и в синхронных точках записи (`set_splits`, «Tanyşdym»). Вдобавок — условный `UniqueConstraint` по `(kind, scope_year, scope_week)` для открытых 2b и 3 и по `(kind, scope_date)` для 4 и 5a. Прецедент — `kind='gate'` в спеке garawul. Что фильтрованный индекс работает на MSSQL, проверить при реализации.

**Изменения плана** приходят из `greenhouse`, а он не может вызывать `export`. Поэтому 2b и повторная 3 создаются beat-задачей каждые 30 минут (`sync_plan_review_tasks`) и сразу в `set_splits`.

### Решения, принятые при реализации

Для каждого решения указано, во что оно обойдётся, если окажется неверным.

- **Коммиты отложены.** Все задачи, которым нужна `0085`, ждут коммита миграций garawul. Если это решение неверно, коммитить придётся одной большой пачкой позже.
- **Дополнительный тест прав.** В Task 7 добавлен тест на `seed_permissions` для `transport.plan`. Цена: один лишний тест.
- **Побочное применение чужой миграции.** `migrate core` заодно применил незакоммиченную `0068` сессии упаковки, потому что `0069` от неё зависит. Владелец предупреждён. Цена: `0068` больше нельзя править на месте.
- **Тестовая обвязка.** Изолированный запуск тестов выставляет `DJANGO_TESTING=true`. Иначе миграция `core/0012` засевает лишнюю строку и `tests_boss_access` падает ложно.
- **Коммиты фронтенда.** Отложены вместе с бэкендом, чтобы каждый коммит был согласован сам с собой.
- **Баннер ревью.** Стоит отдельным блоком над секцией машин, а не внутри Collapse, чтобы свёрнутая секция не прятала открытое ревью. Цена: правка вёрстки.
- **Кто нажимает «Tanyşdym».** Исполнитель (export_manager для ревью, transport для транспорта), а также admin, boss и director. Подтверждено владельцем 2026-09-29. Export manager не может закрыть задачу транспорта.
- **409 при изменившихся данных.** Если данные изменились после открытия страницы, «Tanyşdym» получает 409, и страница перезагружается.
- **Накопление в «Мои задачи» (#5) не исправлено.** Обрезка на 1000 строк существовала и раньше. Замер 2026-09-29: 166 строк в представлении «все роли». Цена: позже в сезоне у export manager в виде «все роли» может пропасть сегодняшняя карточка; обход — выбрать фильтр роли.

### Отложенные мелкие замечания ревью

- Состояние `blocked` обходит защиту от дублей (только через API, в UI такого пути нет).
- Задачи «Tanyşdym» не закрываются сами после своей недели.
- После `set_splits` баннер может показываться с пустым списком изменений.
- Ревью возникает и за уже прошедшие дни текущей недели.
