# Редизайн страницы груза (ShipmentDetail) — дизайн

**Дата:** 2026-07-20
**Экран:** `/export/shipments/:id` — [`frontend/src/pages/export/ShipmentDetail.tsx`](../../../frontend/src/pages/export/ShipmentDetail.tsx)
**Исследование-основание:** [`docs/shipment_detail_ux_research.md`](../../shipment_detail_ux_research.md)

Спека на русском (её ревьюит заказчик), технические имена — как в коде.

## 1. Задача

Дословно от заказчика: страница нужна такая, чтобы **сразу было видно детали**, чтобы было **удобно вводить информацию**, и чтобы когда данные уже введены — **видеть, что по чём и что не заполнено**.

Сегодняшняя страница отвечает этим требованиям плохо:

- она **гармошка** — раскрыт только блок текущего этапа, остальные скрыты ([`ShipmentDetail.tsx:398`](../../../frontend/src/pages/export/ShipmentDetail.tsx#L398)). «Сразу видно» не получается;
- 24 поля всегда выглядят как поля ввода — читать такую страницу тяжело;
- **незаполненные поля ничем не выделены** — понять, чего не хватает, можно только глазами по всей странице;
- сохранение молчаливое: спиннер на время запроса и всё ([`DetailFieldRow.tsx:173`](../../../frontend/src/components/shipment/DetailFieldRow.tsx#L173)).

## 3. Откуда берётся «не заполнено» — ключевое

**Новую таблицу правил заводить не нужно.** Требования «какое поле обязательно на каком шаге» уже описаны в модели `TaskRule` ([`backend/apps/export/models/task.py:47-95`](../../../backend/apps/export/models/task.py#L47-L95)):

| Колонка | Смысл |
|---|---|
| `step` | статус, на котором правило срабатывает |
| `target_fields` | CSV полей, которые должны быть заполнены |
| `assignee_role` | чья это работа |
| `deadline_rule` | срок |
| `condition_field` / `condition_value` | условие применимости правила |

Правила засеяны на каждый шаг жизненного цикла ([`seed_task_rules.py`](../../../backend/apps/export/management/commands/seed_task_rules.py)) — например на `yuklenme` висит `tasks.fill_loading_data` с `target_fields = 'shipment_code,block_sources,variety,weight_net'`.

### Почему именно этот источник

- ничего не дублируется — правила уже ведут задачи и уведомления;
- админ меняет их **без деплоя**;
- подсветка на странице автоматически совпадает с тем, что сотрудник видит в «Моих задачах».

### Правило реализации (важно)

Читать **напрямую из `TaskRule`**, а не из созданных строк `Task`.

Причина: при редактировании правила уже созданные `Task` остаются со старым снимком полей и лечатся только командой `reconcile_tasks` — это известная особенность системы. Если считать подсветку от живых правил, она не врёт никогда, независимо от состояния задач.

Исключение — **задачи с пустым `target_fields`** (например `tasks.give_documents`, `tasks.submit_sales_report`). Подсвечивать нечего, поэтому они берутся из `Task` и показываются списком с ручной отметкой.

### Определение «просрочено»

Поле считается просроченным, если:

1. оно входит в `target_fields` правила, чей `step` — текущий статус груза **или любой уже пройденный**, и
2. условие правила (`condition_field` / `condition_value`) выполняется для этого груза, и
3. значение поля на грузе пустое (`null`, `''`, отсутствует связь).

Поля будущих шагов **не подсвечиваются** — они показываются серым с пометкой «этап ещё не наступил».

### Новое поле API

`ShipmentDetailSerializer` отдаёт вычисляемый блок:

```json
"completeness": {
  "required_total": 20,
  "filled_count": 16,
  "missing_fields": [
    { "key": "pallet_count", "label_key": "…", "step": "yuklenme", "role": "loading_dept_head" }
  ],
  "manual_tasks": [
    { "id": 412, "title_key": "tasks.give_documents", "role": "transport", "is_overdue": false }
  ]
}
```

Считается в сервисе (не во вьюхе), одним проходом по правилам без запроса на каждое поле.

**Область видимости:** сводка **глобальная, не по ролям** — показывает всё недостающее всем. Осознанное решение: менеджеру нужна полная картина по грузу.

## 4. Раскладка

```
┌──────────────────────────────────────────────────────┐
│ ШАПКА: код · статус · маршрут · 💬 Обсуждение · кнопки│
├──────────────────────────────────────────────────────┤
│ СВОДКА                                               │
│   ▓▓▓▓▓▓▓░░ Заполнено 16 из 20                       │
│   Не хватает: [Паллеты][Коробки][Дней в пути]        │
│   Задачи:  ☐ Передать документы  ☐ Сдать отчёт       │
├───────────────────────────────────┬──────────────────┤
│ Назначение      │ Документы       │  ЛЕНТА МАРШРУТА  │
│ Погрузка        │ В пути          │  (та же, плотнее)│
├───────────────────────────────────┴──────────────────┤
│ ПРОДАЖА — на всю ширину                              │
├──────────────────────────────────────────────────────┤
│ Таможенные расходы — таблица на всю ширину           │
├──────────────────────────────────────────────────────┤
│ История изменений →                                  │
└──────────────────────────────────────────────────────┘
```

**Почему «Продажа» на всю ширину, а не карточкой в сетке.** Когда груз реально продаётся, там разворачивается форма отчёта: позиции товара плюс таблица расходов по категориям. В половину колонки это не помещается. Пока этап не наступил — секция схлопнута в одну серую строку.

**Группы** — те же пять, названия по этапам пути: Назначение, Документы, Погрузка, В пути, Продажа. Плюс Заметки.

**Плашки в сводке кликабельны** — прокручивают к полю и сразу открывают его на редактирование. Якоря уже есть: у каждой строки стабильный `id="detail-field-<key>"` ([`DetailFieldRow.tsx:143`](../../../frontend/src/components/shipment/DetailFieldRow.tsx#L143)).

## 5. Поведение ввода

**По умолчанию** значение — просто текст, без рамки. Страница читается как таблица.

**Клик по значению** превращает его в поле ввода:

| Тип | Поведение по клику |
|---|---|
| текст / число / textarea | становится input, курсор внутрь |
| список (`select`, `option_select`) | сразу открывается выпадашка, без второго клика |
| дата | сразу открывается календарь |
| да/нет | переключается сразу, без режима правки |

**Tab** переводит на следующее поле и **сразу открывает его** на редактирование — чтобы заполнять подряд без мыши. Только десктоп.

**Сохранение** — как сейчас: текст/число дебаунс 700 мс + флаш по уходу фокуса, списки/даты сразу.

**Три состояния строки вместо нынешнего спиннера:**

1. в процессе — спиннер;
2. сохранено — надпись **«Сохранено»** рядом с полем, **не исчезает** до следующей правки;
3. ошибка — красная плашка с кнопкой «Повторить». Сейчас ошибка не видна вообще.

Пункт 3 важнее всего на медленных каналах в KZ/RU: сегодня оператор вводит вес, спиннер пропадает, и никаких доказательств, что значение сохранилось.

**Мобильный:** Tab нет, поэтому тап по каждому полю. Лента маршрута на телефоне должна **показываться** (сейчас пропадает вместе со всей правой колонкой — [`ShipmentDetail.tsx:507`](../../../frontend/src/pages/export/ShipmentDetail.tsx#L507)); размещается свёрнутой над карточками.

**Права** — без изменений: если у роли нет прав на поле, оно рендерится как текст и не реагирует на клик.

## 6. Комментарии и задачи

Механика **целиком переиспользуется из Sheet**, нового кода почти нет.

| Элемент | Источник |
|---|---|
| Кнопка «💬 Обсуждение» в шапке | `CommentsDrawer`, `field_key = null` |
| Значок 💬 на строке поля | тот же drawer, `field_key = <ключ поля>` |
| Числа на значках | `comment_counts` — уже считается одним сгруппированным запросом |
| Задачи-галочки в сводке | `Task` с пустым `target_fields` |

Значок 💬 появляется при наведении на строку. Если по полю уже есть переписка — синий, с числом, виден всегда.

Упоминания `@user:42`, `@role:transport` и ссылки `#cell:<key>` работают как в Sheet — формат хранения не меняется.

`CommentsDrawer` сейчас лежит в `components/sheet/`. Его надо поднять в общее место (`components/comments/`), потому что он перестаёт быть частью Sheet.

## 7. Лента маршрута

Заказчик выбрал: **логику не трогать, стиль подогнать**. Граница зафиксирована явно.

**Не меняется** (это и есть одобренный вид): вертикальная лента сверху вниз; круглые точки с ✓ / ● / номером; зелёный = пройдено, синий = сейчас, серый контур = впереди; зелёная линия-соединитель; время под названием шага моноширинным; комментарий перехода; красная плашка отмены; 13 шагов плюс вставка перегрузки при `has_peregruz`.

**Меняется** (только оформление): диаметр точки 32 → 24 px; размеры шрифтов под новые карточки; отступы; рамка и заголовок карточки; ширина колонки.

Проверка: старый и новый скриншот рядом должны читаться как одна и та же лента, просто плотнее.

## 8. Баги, найденные по ходу — чинятся здесь

1. **Полей водителя нет на странице.** `target_fields` требуют `driver_name`, `driver_phone`, `truck_plate`, а в [`shipmentEditConfig.ts`](../../../frontend/src/constants/shipmentEditConfig.ts) их нет. Система требует заполнить то, чего на экране не существует. → добавить в группу «В пути».
2. **Лента маршрута исчезает на телефоне** ([`ShipmentDetail.tsx:507`](../../../frontend/src/pages/export/ShipmentDetail.tsx#L507)). → показывать.
3. **Карточка «Ссылки» — заглушка**: три захардкоженных пункта без данных ([`ShipmentDetail.tsx:510-525`](../../../frontend/src/pages/export/ShipmentDetail.tsx#L510-L525)). → удалить.
4. **Комментарий в коде врёт**: [`ShipmentDetail.tsx:157-161`](../../../frontend/src/pages/export/ShipmentDetail.tsx#L157-L161) утверждает «No accordion», хотя страница — гармошка. → удалить вместе с гармошкой.
5. **Устаревшая документация**: `docs/obsidian/screens/shipment-list-vs-sheet.md` описывает вкладки, `ShipmentEditDrawer` и `?tab=` — ничего этого в коде нет. `docs/SPRINT_PLAN.md:16` тоже говорит про вкладки. → привести в соответствие.

**Доступность.** Раз гармошка уходит, требования ARIA к раскрывающимся блокам («R3» из исследования) отпадают. Для оставшихся сворачиваемых элементов (Продажа до наступления этапа, лента на мобильном) действует контракт W3C: `aria-expanded`, `aria-controls`, заголовок с `aria-level`, панель с `role="region"`.

## 10. Не входит в объём

- **Куда ведут уведомления.** Ссылки указывают в Sheet (`/export/shipments/sheet?shipment=…`). После этой работы у комментария два места жительства. Решается отдельно, на дизайн не влияет.
- **Автооткрытие нужного этапа по роли** (R1/R9 из исследования) — гармошки больше нет, всё видно сразу, проблема снимается сама.
- **Фильтр сводки «только моё»** — сознательно не делаем.
- **Правка правил `TaskRule` из интерфейса** — только через админку, как сейчас.

## 11. Открытые вопросы

1. **Полнота правил.** Подсветка честна ровно настолько, насколько полны `TaskRule`. Перед запуском нужно пройтись по засеянным правилам и проверить, что для каждого этапа перечислены действительно все обязательные поля. Это не программирование, это сверка с тем, как работают люди.
2. **Считать ли просроченными поля пройденных этапов.** Спека говорит «да» — иначе пропущенное на погрузке поле навсегда исчезнет из виду. Но если так всплывёт много исторических дыр, старые грузы будут выглядеть тревожно. Проверить на реальных данных.
3. **Пользуются ли страницей с телефона и какие роли** — от этого зависит, сколько сил вкладывать в мобильную раскладку.
