# Упаковка: присоединить, отсоединить, поменять — design

**Date:** 2026-09-29
**Status:** approved in chat, not implemented
**Builds on:** `docs/SHIPMENT_THREE_PARTS_RU.md` — это подпроект **(b)**: упаковка присоединяется
поздно (R4) и меняется между машинами (R5).

## Problem

Сегодня упаковку (план поставки) можно присоединить к экспортной части (план назначения)
только пока **обе** строки в Подготовке (`draft`), и обратно её не снять:

1. `_validate_join` / `_execute_join` (`backend/apps/export/views.py`) требуют `draft` у обеих
   строк, переносят блоки в план назначения и **удаляют** строку плана поставки.
2. `transition_to` (`backend/apps/export/services/shipment.py`, «Two-row join guard») не
   выпускает шипмент из `draft` без блоков. Значит, документы нельзя начать, пока
   Солтанмырат не дал упаковку — а по процессу документы идут первыми (R4).
3. Swap на Sheet (`/swap/`, `swap_config.py`) меняет местами плоские поля и **не трогает блоки** —
   упаковку им не поменять.
4. Доска `/export/assign` сопоставляет план с **тестовым** «Спросом» (`MOCK_DEMAND`) и её
   «Подтвердить» просто двигает статус через `/assign/`. Присоединять на ней нечего.

## Decisions taken

| Вопрос | Ответ |
|---|---|
| Когда можно присоединить упаковку | В любой момент **до погрузки**: план назначения в `draft`, `gumruk_girish` или `gumruk_chykysh` |
| Что ещё нужно | Отсоединить и **прямой обмен** упаковкой между двумя машинами |
| Модель данных | **Перенос** (не ссылка): упаковка живёт на той строке, где она сейчас; операции её переносят |
| Нетто/брутто после старта документов | **Не меняются**, кроме пустого нетто — оно заполняется из упаковки. В `draft` нетто пересчитывается из блоков, как сейчас. Документы берут вес из шаблона брутто/нетто |
| Правая колонка доски | Тестовый «Спрос» **заменяется** планами назначения |
| Swap на Sheet | Меняет **только упаковку**. Старый обмен полями удаляется |
| Join на Sheet | Расширяется до «до погрузки», как на доске |
| Роли | `JOIN_ROLES` + `loading_dept_head` + `loading_dept_head_deputy` (для join, unjoin, swap — везде) |

Почему «перенос», а не «ссылка»: при ссылке все, кто читает блоки шипмента (CMR / инвойс /
упаковочный лист, Gaplama «Tıra giden», факт недельного плана, строки Sheet, правила задач),
должны ходить по ссылке, а присоединённые планы поставки навсегда висят в `draft` и путают
счётчики. При переносе всё это читает ту же строку, что и сегодня.

Цена переноса (принята): после присоединения строка плана поставки удаляется, как сейчас.
При отсоединении создаётся **новая** строка с **новым** кодом. Автор исходного плана
поставки после присоединения неизвестен, поэтому уведомления об отсоединении и обмене идут
**роли**, а не автору.

## Terms

- **Упаковка** — это набор данных, который переносится целиком:
  `block_sources` (блок + кг + `harvest_date` блока), `export_code`, `variety`,
  `varieties_dominant`, `harvest_date`, `harvest_status`, `weight_to_load_kg`.
  Всё остальное (страна, клиент, фирмы/`firm_splits`, машина, водитель, документы) остаётся
  на своей строке.
- **Строка с упаковкой** — у шипмента есть хотя бы один `block_sources`.
- **Свободный план поставки** — `draft`, есть упаковка, нет страны или клиента.
- **План назначения** — есть страна и клиент.
- **До погрузки** — статус в `PRE_LOADING = {'draft', 'gumruk_girish', 'gumruk_chykysh'}`.
- **Документы начаты** — статус не `draft`.
- **Вес упаковки** `packaging_weight(row)` — считается **до** переноса: сумма `weight_kg` блоков,
  если все блоки взвешены; иначе, если строка в `draft`, — её `weight_net` (в `draft` он
  взят из упаковки: supply-first план хранит итог в `weight_net`, а блоки без кг); иначе —
  сумма взвешенных блоков или `null`, если таких нет.
- **Правило нетто для всех трёх операций:**
  - строка в `draft` после операции получает `weight_net = packaging_weight` упаковки,
    которая на ней оказалась (нет упаковки → `null`);
  - строка не в `draft`: если `weight_net` пустой и упаковка пришла — заполнить
    `packaging_weight`; если уже заполнен — не трогать (решение 2026-09-29);
  - `weight_gross` не трогается никогда — это не часть упаковки.

  Почему заполнение пустого нетто безопасно: документы берут брутто/нетто из шаблона
  `Shipment.packing_template` (`PackingTemplate`), а сырые `weight_net` / `weight_gross` —
  только когда в шаблоне поля нет (`build_cmr_context`,
  `backend/apps/contracts/services/document_context.py`). Кроме того, при погрузке
  `close_pallet_manifest` перезаписывает `weight_net` реальным весом паллет — значение до
  погрузки всегда предварительное.

## Part 1 — Backend

### 1.1 Барьер переезжает (`transition_to`)

- Выход из `draft` (кроме `cancelled`) требует только `country` + `customer`. Требование
  `block_sources` отсюда убирается.
- Переход `gumruk_chykysh → yuklenme` требует упаковку. Иначе `ValueError` с текстом
  `PACKING_NOT_JOINED` («Packing not joined: …» — по-английски, как все сообщения бэкенда;
  Sheet показывает его тостом через `extractPatchError`).
- Правило общее для ручного `/transition/`, `/assign/` и auto-advance (всё идёт через
  `transition_to`). Gapy — то же правило.

**Видимая ошибка вместо тихого зависания.** `auto_advance_if_ready` глотает `ValueError`,
поэтому если ввести `loading_started_at` на шипменте без упаковки, поле запишется, а статус
молча останется `gumruk_chykysh`. Поэтому запись `loading_started_at` на строке **в
`PRE_LOADING`** без упаковки **отклоняется в `ShipmentPatchSerializer`** с той же ошибкой.
Строки на `yuklenme` и дальше не проверяются (у старых импортов из Excel блоков может не
быть — правка их поля не должна давать 400). Скан QR (`/shipments/{id}/scan/`)
`loading_started_at` **не пишет** (`SCAN_FIELDS` начинаются с `border_crossed_at`), поэтому
его не касается. Других записей `loading_started_at` в runtime-коде нет (только импорт и
seed).

### 1.2 Присоединить — `POST /shipments/{target}/join/` (расширяем)

Тело не меняется: `{ "source_id": <int> }`.

Проверки (дешёвые в `_validate_join`, авторитетные — повторно под `select_for_update`):

- `target.status ∈ PRE_LOADING`, есть страна и клиент, **нет упаковки**, **нет паллет**.
- `source.status == 'draft'`, есть упаковка, нет паллет.
- Разные строки; сезон открыт у обеих (как сейчас).

Действие — как сегодня (перенос блоков и полей упаковки «только если у target пусто»,
удаление source, уведомление автору source, запись в журнал target), с одним изменением:

- **Нетто:** по правилу нетто (Terms). Для `target` в `draft` это совпадает с сегодняшним
  пересчётом; после старта документов пустое `weight_net` заполняется, заполненное —
  **не трогается**.
- Статус **не двигается**, `auto_advance_if_ready` **не вызывается**.

### 1.3 Отсоединить — `POST /shipments/{id}/unjoin/` (новый)

Проверки: статус `∈ PRE_LOADING`, есть страна и клиент, есть упаковка, нет паллет,
сезон открыт.

Действие (одна транзакция, строка под `select_for_update`):

1. Создать новую строку: `draft`, тот же сезон и `date`, новый код
   `generate_shipment_code(today=<date исходной строки>)` — дата в коде (`DDMM`) та же, что у
   исходной строки, потому что факт недельного плана (`actual_rollup`) считает кг по дате
   **из кода** шипмента, на котором лежат блоки. `created_by` = кто нажал, запись «Created in Preparation»
   в `ShipmentStatusLog`, задачи `generate_tasks_for_status(new, 'draft')` — как у
   создания плана поставки. С `b318f0d8` у строки без страны и клиента (packing part)
   draft-задач нет — так и должно быть. У исходной строки назначение остаётся, её задачи
   не трогаются.
2. Перенести на неё упаковку (`block_sources.update(shipment=new)` + поля упаковки + M2M).
   Её `weight_net` = `packaging_weight(исходная строка)`.
3. Очистить упаковку на исходной строке. Нетто — по правилу нетто (в `draft` → `null`,
   иначе не трогать).
4. Журнал на обеих строках, уведомления (§1.5).

Ответ: `200` с деталями **исходной** строки + `new_supply_id` + `new_supply_code`.

### 1.4 Поменять упаковку — `POST /shipments/{a}/swap-packaging/` (новый, заменяет `/swap/`)

Тело: `{ "other_id": <int> }`.

Проверки: `a ≠ b`, обе `∈ PRE_LOADING`, у обеих есть упаковка, ни у одной нет паллет,
сезон открыт у обеих. Второй строкой может быть и свободный план поставки — тогда это
«заменить упаковку на машине».

Действие (одна транзакция, обе строки под `select_for_update` в порядке pk):

1. Поменять местами `block_sources`: прочитать строки обеих сторон (`block`, `weight_kg`,
   `harvest_date`), удалить их и создать заново на противоположной стороне
   `bulk_create(batch_size=500)`. Не `UPDATE shipment=...` по очереди: одинаковый блок с одной
   датой на обеих строках упрётся в `unique_together (shipment, block, harvest_date)`, а
   «временного» шипмента для промежуточного переноса нет (FK не `null`). На
   `ShipmentBlockSource` никто не ссылается по FK, поэтому пересоздание безопасно.
   Затем поменять поля упаковки и `varieties_dominant`.
2. Нетто по каждой строке отдельно, по правилу нетто: `packaging_weight` обеих строк
   считается до обмена; строка в `draft` получает вес пришедшей упаковки, строка не в
   `draft` — только если её нетто пустое.
3. Журнал на обеих строках, уведомления (§1.5).

Ответ: `200` с деталями обеих строк.

### 1.5 Уведомления и журнал

- Присоединить — как сейчас: автору плана поставки.
- Отсоединить / поменять — всем активным `loading_dept_head`; если документы начаты хотя бы
  у одной из строк — ещё `document_team`. Нажавшему не шлём. Ссылка — на шипмент.
- Каждая операция пишет `ShipmentStatusLog` (статус не меняется) на каждую затронутую
  строку, с кодами второй строки в комментарии.

### 1.6 Права

- `apps.core.roles.JOIN_ROLES` расширяется на `loading_dept_head`, `loading_dept_head_deputy`.
  Все три эндпоинта (`join`, `unjoin`, `swap-packaging`) проверяют его (+ суперюзер), как
  сейчас `join`. На 2026-09-29 `JOIN_ROLES` читает только `join` (`views.py`) — перед
  расширением повторить grep.
- `get_permissions`: `unjoin` и `swap-packaging` получают ту же ветку, что `join` —
  `resource_edit_permission('shipment')`. Без этого общий `DynamicResourcePermission`
  отображает POST на `shipment.can_create` и отдаёт 403 ролям без права создания (F12/F19).
  Проверить, что у `loading_dept_head` и заместителя есть `shipment.can_edit`.
- Фронт: `JOIN_ROLES` в `frontend/src/components/sheet/joinHelpers.ts` — тот же список.
- Доступ к странице `export.assign` для `loading_dept_head` и заместителя — грант в матрице
  прав (данные). Проверить touch-list новой роли на странице (сайдбар, `PAGE_REGISTRY`).

### 1.7 Удаляется

- `POST /shipments/{id}/swap/`, `GET /shipments/swappable-fields/`, `swap_config.py`,
  `ShipmentSwapSerializer` и их тесты.

## Part 2 — Доска `/export/assign`

Файл: `frontend/src/pages/export/AssignmentBoard.tsx` (+ `assignment/*`).

1. **Слева — свободные планы поставки.** Карточка: код, блоки + кг, экспорт-код, сорт,
   предупреждения о возрасте томата («вчерашний» / «старый» — как сейчас в `SupplyCard`).
2. **Справа — планы назначения до погрузки**, две группы: **«Ждут упаковку»** и
   **«С упаковкой»**. Карточка: код, страна и клиент, статус, машина и водитель (если
   заполнены — это и есть «экспорт + транспорт»), у второй группы — присоединённая упаковка.
3. **Центр — действие по выбору** (выбрать можно до двух карточек):
   - поставка + назначение без упаковки → **«Присоединить»** (`/join/`);
   - одно назначение с упаковкой → **«Отсоединить»** (`/unjoin/`);
   - две карточки с упаковкой → **«Поменять упаковку»** (`/swap-packaging/`).
   Отсоединить и поменять — через подтверждение с текстом «если QR-наклейки уже напечатаны,
   перепечатайте».
4. **Данные:** один запрос списка шипментов
   `GET /shipments/?status_code__in=draft,gumruk_girish,gumruk_chykysh`. Список сейчас
   умеет только один `status_code` (`views.py`, `get_queryset`) — добавляется
   `status_code__in`. При нём отдаётся `ShipmentDraftListSerializer` (как для
   `status_code=draft`, с тем же prefetch `block_sources`), расширенный полями
   `status_code`, `country`, `customer` (id), `truck_plate`, `driver_name`. Новый хук
   `useJoinBoard()` рядом с `useDrafts()`.
5. **Убирается:** `MOCK_DEMAND`, `DemandCard`, правила совместимости спроса в
   `MatchPanel`, кнопка «Подтвердить» (`useAssignDraft` на доске). Эндпоинт `/assign/`
   **остаётся** — его вызывает `ShipmentDetailHero`.
6. Кнопки — только `canUserJoin(user)`. Закрытый сезон — только чтение
   (`useSeasonReadOnly`).
7. Слово «черновик» в интерфейсе не используется — «план поставки» / «план назначения».

## Part 3 — Sheet

1. **Swap:** выбрали две строки → **«Поменять упаковку»** → подтверждение →
   `/swap-packaging/`. `SwapFieldsModal` и `swapFieldGroups.ts` удаляются, `SwapActionBar`
   упрощается до одной кнопки.
2. **Join:** `isDestinationDraft` / `explainJoinBlockers` в `joinHelpers.ts` принимают
   target в любом статусе `PRE_LOADING` (не только `draft`), без упаковки и с
   страной/клиентом. Source по-прежнему только `draft`.

## Known effects (проверить в плане, не менять молча)

- **Каскад после снятия барьера (коммит 1).** Сегодня план назначения без блоков застревает
  в `draft`, даже если его следующий триггер уже заполнен (`documents_status`, дальше
  `customs_exit_at`). После снятия барьера при первом же сохранении такая строка
  прыгнет на один-два статуса (`auto_advance_if_ready` проходит все выполненные шаги).
  **Перед деплоем на live** посчитать такие строки: `draft`, есть страна и клиент, нет
  `block_sources`, заполнен триггер `draft → gumruk_girish`. Если их больше нуля —
  показать список владельцу до деплоя.

- **Факт недельного плана.** `actual_rollup` (`apps/greenhouse/services/actual_rollup.py`)
  считает кг по дате, закодированной в `shipment_code` шипмента, на котором сейчас лежат
  блоки. Join и обмен между машинами **разных дней** переносят кг на другой день — сегодня
  Join делает то же самое, это принято. Отсоединение день **не** меняет (код новой строки
  берёт дату исходной). Лимит прогноза (`assert_draw_within_pool`) проверяется только при
  создании плана поставки; перенос его не перепроверяет.
- **Квоты.** `firm_splits` не переносятся при unjoin/swap, поэтому `QuotaUsageRecord` не
  затрагивается. Join сохраняет сегодняшнее правило «firm_splits source → target, если у
  target пусто».
- **Паллеты** создаются при погрузке (`Pallet`, weight_master). Запрет при наличии паллет —
  страховка на случай раннего ввода.
