# Автонумерация инвойсов по фирме и году — design

**Date:** 2026-10-03
**Status:** approved in chat 2026-10-03, spec awaiting review, not built
**Builds on:** ADR-023 (продажа = доля фирмы в машине), Slice 4 «Привязать»
(`backend/apps/contracts/services/shipment_firm_contracts.py::link_split_to_contract`).

## Problem

Номер инвойса (`ContractSale.invoice_number`) сегодня никто не выдаёт:

- Продажа, созданная кнопкой «Привязать», остаётся без номера и даты
  (`shipment_firm_contracts.py:239`). 25 из 51 продажи в базе — без номера; инвойс печатается
  с пустым номером и датой.
- Форма ручной продажи подсказывает `contract.last_invoice_number + 1` — счётчик **по контракту**
  (`ContractSaleCreate.tsx:166`, `ContractSalesTab.tsx:73`). В реальности номера идут **по
  экспортной фирме внутри года** (в базе 2026: DM до 288, MA до 300, YGT до 393).
- При смене фирмы у рейса старая продажа не удаляется (`export/views.py:3480` удаляет только
  `ShipmentFirmSplit`) и продолжает считаться в итогах контракта старой фирмы. При отмене рейса
  продажи тоже остаются.

## Decisions taken (owner, 2026-10-03)

| Вопрос | Ответ |
|---|---|
| Область счётчика | Экспортная фирма × календарный год. С 1 января — заново с 1 |
| Когда выдаётся номер | При «Привязать» (создание продажи). Запасной путь — при скачивании инвойса, если номера ещё нет |
| Дата инвойса | Дата рейса (`Shipment.date`); год нумерации — из неё. Можно поправить руками |
| Старт посреди года | Админ вводит «последний использованный номер» на странице «Нумерация инвойсов» (таблица всех фирм) |
| Освободившийся номер (дыра) | **Заполняется** следующей новой продажей — **временно**, вопрос «порядок по датам или без дыр» открыт (см. memory `project_invoice_number_gap_fill_open`) |
| Смена фирмы при привязанном контракте | Предупредить → после подтверждения удалить продажу убранной фирмы и отвязать контракт |
| Отмена рейса | То же: предупредить → удалить продажи всех фирм рейса |
| Разовый контракт при отвязке | Удалить вместе с продажей. **Если к нему загружены сканы** — не удалять, а пометить `cancelled` (вложения удаляются каскадом) |
| Инвойс уже напечатан | Удалять как обычно, но в предупреждении явно написать «инвойс №… уже напечатан» |
| Как удалять (транзакционность) | Вариант A: фронт делает действие как сейчас, затем вызывает endpoint очистки в contracts. Очистка идемпотентна |
| Рамочный контракт через границу года | Не бывает → ограничение `(contract, invoice_number)` остаётся |

## Design

### 1. Счётчик: модель `contracts.InvoiceNumberBase`

| Поле | Тип |
|---|---|
| `export_firm` | FK `core.ExportFirm`, `PROTECT` |
| `year` | `IntegerField` |
| `last_number` | `IntegerField`, default 0 — последний номер, выданный **вне системы** (нижняя граница) |
| `updated_at` / `updated_by` | аудит правки админом |

`UniqueConstraint(export_firm, year)`. Модель живёт в `contracts` (читает `core`, направление
зависимостей соблюдено). Таблица новая — старый код беты в неё не пишет, поэтому
`NOT NULL` без DB-default здесь безопасен.

Строки нет → граница 0 (новый год начинается с 1 без ручных действий). Строка создаётся
`get_or_create` при первой выдаче номера или при сохранении в админке.

### 2. Выдача номера: `contracts/services/invoice_number.py`

```
allocate_invoice_number(export_firm_id, year) -> int
```

1. `get_or_create` строки `(firm, year)`, затем `select_for_update()` на ней — сериализует
   одновременные «Привязать» одной фирмы (паттерн уже работает на MSSQL: `rollup.py:39`,
   `gate.py:204`). Вызывать только внутри `transaction.atomic`.
2. `used` = номера продаж с `contract__export_firm_id = firm`, `invoice_date__year = year`,
   `invoice_number > last_number`.
3. Ответ — наименьшее `n > last_number`, которого нет в `used` (заполнение дыр).

Фирма продажи определяется через `contract.export_firm` (не `sale.export_firm` — тот nullable).

Точки вызова:
- **`link_split_to_contract`**: если у продажи нет номера — `invoice_date = shipment.date`
  (если пусто), `invoice_number = allocate(firm, invoice_date.year)`. Повторное «Привязать»
  (смена контракта той же фирмы) номер **не меняет**.
- **Скачивание инвойса** (`ContractSaleViewSet.document` с `type=invoice_*` и
  `ShipmentPacketZipView`): если номера нет — выдать (дата = дата инвойса, иначе дата рейса,
  иначе сегодня). Покрывает 25 старых продаж без номера и ручные продажи. Продажа закрытого
  сезона номер **не** получает (запрет записи D1) — документ печатается как сейчас.
  CMR и TIR-карнет тоже печатают номера всех фактур машины (`document_context.py` ~514, ~834),
  поэтому при их скачивании живые продажи машины тоже получают номер (без отметки «напечатан»).
- **Ручная продажа** (`ContractSaleCreateSerializer.create`): пустой номер → выдать.

Ручной номер разрешён. Валидация в `ContractSaleCreateSerializer`: номер уже занят у этой фирмы
в этом году (кроме самой продажи) → **400**, не 500. Год = год `invoice_date`, иначе текущий.

### 3. Отметка «инвойс напечатан»

`ContractSale.invoice_printed_at = DateTimeField(null=True, blank=True)` — ставится при первом
скачивании инвойса в **обоих** путях: `ContractSaleViewSet.document` (`type` начинается с
`invoice`) и `ShipmentPacketZipView` (для каждой продажи пакета). Поле nullable — бета со старым
кодом его не ломает.

### 4. Очистка осиротевших продаж: `release_orphan_sales(shipment)`

Сервис в `contracts/services/shipment_firm_contracts.py`. Сирота — продажа, у которой
`shipment_id = shipment.id` **и** (рейс в статусе `cancelled` **или** `contract.export_firm`
нет среди текущих `shipment.firm_splits`).

- Продажи без рейса (`shipment_id IS NULL`, импорт из Excel) **не трогаются никогда** — условие
  на `shipment_id` обязательно.
- Для каждой сироты: `sale.delete()` (строки позиций уходят каскадом, `rollup` пересчитывает
  итоги контракта). Затем, если контракт `ONE_TIME` и продаж у него больше нет: есть вложения →
  `status = cancelled`; нет → удалить контракт.
- Идемпотентна: повторный вызов ничего не делает.

Вызовы:
- Новый endpoint `POST /api/v1/contracts/shipments/{id}/release-sales/` → `{released: [{export_firm,
  contract_number, invoice_number}], contracts_deleted, contracts_cancelled}`. Права — resource
  `shipment` (как у `firm-splits`, `export/views.py:207`), а не удаление `sale`: очистка только
  приводит продажи в соответствие с уже сделанным действием, и тот, кто меняет фирмы, может не
  иметь права удалять продажи.
- В начале `link_split_to_contract` — бесплатная повторная попытка, если вызов с фронта упал.

Направление зависимостей: export не знает о продажах; очистку запускает contracts (по вызову
фронта). В `backend/CLAUDE.md` §3 пример разрешает export→contracts — это противоречит строгому
списку выше него; следуем строгому списку.

### 5. Предупреждение на фронте

Данные для окна даёт **тот же** endpoint очистки в режиме предпросмотра:
`GET /api/v1/contracts/shipments/{id}/release-sales/?keep=<id,id>` (фирмы, которые останутся)
или `?cancel=1` → список продаж, которые будут удалены: `export_firm_code`, `contract_number`,
`invoice_number`, `invoice_printed`. (Уточнение 2026-10-03 при планировании: изначально —
расширить `GET shipment-firm-contracts`, но он закрыт правом `sale`, а смену фирм делает право
`shipment`; предпросмотр на том же endpoint держит одно право на оба шага.)

Одна общая обёртка (хук) для **всех** путей изменения фирм и отмены:
`useSheetCellWrite` (редактор Sheet, включая вставку), `useSetFirmSplits`
(`ShipmentFirmSelector` на странице рейса), `useApplyUndo` (Ctrl+Z — удалённые продажи откат
не вернёт, поэтому тоже через предупреждение), отмена рейса (`useShipments.ts` → `/cancel/`).

1. Получить привязки рейса; вычислить затронутые фирмы (убранные из долей; при отмене — все).
2. Затронутых нет → действие как сейчас, без окна.
3. Есть → окно подтверждения: фирма, № контракта, № инвойса, «уже напечатан» для отмеченных.
4. Подтвердили → действие (`firm-splits` / `cancel`) → при успехе `release-sales`.
   Ошибка `release-sales` → toast; сироту уберёт следующий вызов.

Тексты в ru/tk/en. Слово «черновик/draft» в UI не используется.

### 6. Админка «Нумерация инвойсов»

Страница в `frontend/src/pages/admin/`: все экспортные фирмы × выбранный год (по умолчанию
текущий), колонки «Фирма | Год | Последний номер», правка в ячейке. Backend: list + upsert по
`(export_firm, year)`. Страница открывается кнопкой на списке экспортных фирм и закрыта правом
страницы `admin.firms` — как «Правовые формы» (`/admin/legal-forms`), без нового кода в
`PAGE_REGISTRY` и без миграции прав. **Править** может только роль `admin` (и superuser):
backend `write_permission('admin')`, на фронте ячейки только для чтения у остальных.

**Data-миграция:** предзаполняет `last_number` для каждой `(фирма, год)` максимумом номера из
базы. Это **только нижняя граница**: в базе 26 пронумерованных продаж за 2026 год, а Excel
выдал намного больше.

### 7. Форма ручной продажи

Убрать подсказку «последний номер контракта + 1» в `ContractSaleCreate.tsx` и
`ContractSalesTab.tsx`. Поле номера необязательное; пусто → номер выдаёт система. Поле
`Contract.last_invoice_number` и его rollup не трогаем.

## Deploy

1. `migrate contracts` (номер миграции проверить перед написанием — общий tree).
2. **До того как код выдачи номеров попадёт в общий tree** (dev, бета и все локальные
   runserver'ы работают с одной живой базой): админ вписывает реальные последние номера из Excel
   для всех фирм за 2026 год. Иначе первые машины получат номера, которые уже есть на бумаге.
   В плане это отдельная остановка между админ-страницей и выдачей номеров.

## Testing

Backend:
- `allocate_invoice_number`: граница; заполнение дыры; новый год с 1; фирмы независимы; строка
  без записи = 0; номера ниже границы игнорируются.
- `link_split_to_contract`: выдаёт номер и дату рейса; повторное «Привязать» с другим контрактом
  номер сохраняет.
- Валидация: занятый номер у фирмы/года → 400.
- `release_orphan_sales`: убранная фирма удаляется, оставшаяся — нет; отмена удаляет все;
  продажа с `shipment_id IS NULL` не трогается; разовый контракт без вложений удаляется, с
  вложениями → `cancelled`; рамочный остаётся; повторный вызов — no-op.
- `invoice_printed_at` ставится в обоих путях скачивания.

Frontend:
- Обёртка: нет затронутых → без окна; есть → окно с номерами и пометкой «напечатан»; отказ →
  действие не выполняется; успех → вызывается `release-sales`.
- Админ-страница: список и сохранение ячейки.

## Out of scope

- Порядок номеров по датам вместо заполнения дыр (открытый вопрос, переключение = только
  функция выдачи).
- Перенумерация при смене даты рейса или даты инвойса.
- Мягко удалённые рейсы (`deleted_at`) и уже существующие сироты на других рейсах — очистка
  сработает для рейса только при следующем вызове на нём.
- Дыры в номерах контрактов (`next_contract_seq`) — отдельная тема.
