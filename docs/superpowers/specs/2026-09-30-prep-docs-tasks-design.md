## 1. Что меняется в движке задач

Сейчас задачи создаются одним набором при входе отгрузки в статус. Шаг двигается дальше, когда закрыты все его задачи, кроме ручных. Для списка 5b–22 этого мало. Нужны четыре добавки:

| # | Добавка | Зачем |
|---|---|---|
| E1 | **`TaskRule.depends_on`** — CSV из `title_key`. Правило с зависимостями не создаётся при входе в шаг. Оно создаётся, когда отгрузка стоит на его шаге **и** все зависимости выполнены | «Задача после N» (решение владельца: появляется, когда N сделана) |
| E2 | **Новое правило завершения `confirm`** — кнопка, которая **держит** шаг. Сейчас ручная `manual_done` шаг не держит | Почти вся DOCS — кнопки («Taýýarladym», «Ugradyldy», «Geldi»). Без этого статус уехал бы, не дожидаясь их |
| E3 | **Страховка авто-перехода.** Шаг считается не выполненным, пока есть правило этого шага с зависимостями, задача по которому ещё не создана | Иначе статус сдвинется в промежутке между «закрылась N» и «появилась задача после N» |
| E4 | **`TaskRule.gates_step`** (по умолчанию «да»). Задача с `gates_step=False` закрывается сама по полю, но шаг не держит | П. 6 «присоединить упаковку»: документы можно начинать до упаковки (правило из коммита `8edaec16`), упаковка нужна только для погрузки |

**Когда зависимость D выполнена.** Проверки идут по порядку, срабатывает первая подходящая:
1. У отгрузки есть задача D: выполнена, если она закрыта (или отменена из-за несовпадения условия).
2. Задачи D нет, а правило D — **этого же** шага, относится к отгрузке и уже действует для неё: **не выполнена**. Задачу создадут, и её надо дождаться.
3. Иначе (правило D с прошлого шага без задачи, или не относится к отгрузке по условию, например вариант Gapy у обычной) — **выполнена**.

Пункт 3 убирает вечную блокировку. Отгрузка вошла в `draft` до новых правил: у неё старая задача transport «водитель» и нет `choose_truck`. Потом она перешла в `gumruk_girish` уже при новых правилах. Задача 11 ждёт `choose_truck`, задачи нет, правило с прошлого шага, поэтому зависимость выполнена, и 11 появляется.

**С какого момента новые правила действуют для отгрузки.**
- У новых правил каталога есть поле `TaskRule.effective_from`. Seed ставит его один раз, при создании правила, и повторные запуски его не переписывают.
- Правило действует для отгрузки, если отгрузка вошла в свой текущий шаг не раньше `effective_from`.
- Время входа в шаг берётся из последней записи журнала статусов (`ShipmentStatusLog`) для этого статуса. У черновика без записей — время создания отгрузки. Поле `status_changed_at` для этого не годится: у нового черновика оно пустое.
- Итог: отгрузка, которая к деплою уже стоит в «Подготовке» или на таможне, доживает этот шаг по старым задачам. На следующем шаге её встречают новые правила.

**Порядок в `Shipment.save()`:** закрыть задачи → создать ждущие (`spawn_ready_tasks`) → авто-переход. Внутри каскада авто-перехода после каждого шага сначала создаются задачи нового шага и его готовые ждущие, и только потом проверяется, выполнен ли этот шаг.

**Где ещё вызываются закрытие и создание ждущих.** Эти пути пишут в БД мимо `Shipment.save()` или создают задачи сами:

| Путь | Что добавить |
|---|---|
| Join / unjoin / swap упаковки (`QuerySet.update`) | закрыть `join_supply` и создать ждущие |
| Создание аванса (`FinansistAdvanceShipment`) | закрыть `give_advance` |
| Контракт у продажи (`ContractSale.contract`) и скачивание договора | проверить `prepare_contract` |
| Скачивание документов (§3) | закрыть задачу печати |
| `reconcile_shipment_tasks` и `sync_draft_tasks_with_destination` (смена Gapy/обычная, поздняя страна) | создавать задачи только через ту же проверку зависимостей, иначе 8.x или 11 появятся раньше времени |

Каждый путь покрывается тестом.

**Кнопка.** Сейчас кнопка «Tamamlandy diý» показывается только у `manual_done`. Теперь она будет и у `confirm`.

## 3. Документы закрывают задачи сами

Эндпоинты документов живут в `contracts`: CMR, TIR, `sales/{id}/document?type=ct1_ru|fito_ru|customs_tk` и договор `contracts/{id}/agreement/`. После успешной генерации они вызывают сервис `export`:

```
mark_document_tasks(shipment, doc, user)
```

Направление зависимости `contracts → export` разрешено.

| Документ | Закрывает |
|---|---|
| CMR | `print_cmr` |
| TIR | `print_tir` |
| `ct1_ru` | `print_ct1` |
| `fito_ru` | `print_phyto` |
| `customs_tk` | `print_customs_request` |
| договор (agreement) | `prepare_contract` — только когда у **каждой** фирмы отгрузки есть контракт и договор этого контракта скачан |

- Скачан хотя бы один документ нужного типа по отгрузке — задача закрыта. CT-1 и fito печатаются по фирме; засчитывается первая.
- «Скачан» — значит, эндпоинт успешно отдал файл (docx или pdf). Заранее «на всякий случай» документ не скачивают, так что это надёжный признак.
- Задача закрывается от имени того, кто скачал.

## 6. Тесты (главное)

- **E1:** 12 появляется только после 9, 10 и 11. У обычной отгрузки 11 ждёт 8.1, у Gapy — 8.2.
- **E2 / E3:** шаг из одних кнопок не уезжает раньше последней кнопки. Статус не сдвигается между «закрылась N» и «появилась задача после N».
- **E4:** `join_supply` не держит `draft`. Документы можно начинать до упаковки.
- **Идущие отгрузки:** отгрузка, вошедшая в шаг до `effective_from`, не получает новых задач этого шага.
- **Переход через деплой:** отгрузка вошла в `draft` до новых правил, а в `gumruk_girish` после. Она доходит до `gumruk_chykysh` без блокировки.
- **Обходные пути:** join, аванс, контракт и сверка по условиям закрывают или создают задачи правильно, по тесту на каждый путь.
- **Документы:** скачивание CMR закрывает `print_cmr`. `prepare_contract` ждёт контракт и договор у **всех** фирм.
- **Эффекты:** 11 ставит «Dowam edýär», 22 ставит «Gümrükden geldi».
- **Полный путь:** обычная отгрузка и Gapy проходят `draft → gumruk_chykysh` только по кнопкам и полям.

## 7. Допущения (поправь, если неверно)

- **A-1.** CT-1 и fito закрываются при скачивании по **первой** фирме, не по всем. Контракт (п. 9), наоборот, нужен у всех фирм.
- **A-2.** Задачу печати закрывает скачивание **любым** пользователем, даже если boss просто открыл CMR посмотреть.
- **A-3.** Скачивание `packet.zip` (весь пакет документов) закрывает все задачи печати, документы которых входят в пакет.
- **A-4.** У новых задач DOCS **срока нет**. Отсчитывать от входа в шаг нельзя: ждущая задача часто появляется, когда такой срок уже прошёл.

## 8. Риски

- **Общая БД с beta.** Новые колонки `TaskRule.depends_on` и `gates_step` добавляются как nullable или с DB-default (урок `0085`). Новые правила `seed_task_rules` запускать только **после** деплоя кода: старый код не знает `confirm` и `depends_on`.
- **Много кликов у document team.** До 13 задач на машину. Это прямое требование списка. Скачивание документов снимает 6 из них без лишних кликов.
- **`set_border_point` выключается.** Если пограничный пункт нужен документам (CMR), его заполнение держится только на привычке. Скажи, если его нужно оставить задачей.
