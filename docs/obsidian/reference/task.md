# Task System

How work reaches a person in this platform. A **Task** is one unit of work for one
role, generated by the system rather than typed in by a manager: nobody assigns
these by hand, and there is no "create task" button anywhere in the UI.

This page is the whole system end to end — the model, the four kinds, what
triggers each one, and what closes it. For the per-step catalog of shipment task
rules (the table of "entering `yuklenme` opens *Fill loading data* for
`loading_dept_head`"), see [[task-rules]]. The same catalog is live in the app at
`/export/task-rules` — see [[../screens/task-rules]].

Source of truth for the code: `backend/apps/export/models/task.py`,
`backend/apps/export/services/task_rules.py`.

## The short version

1. A shipment **enters a status**. That is the only trigger a shipment task has —
   not a date, not a manual click, not a field edit.
2. The engine reads every **active `TaskRule`** whose `step` equals that status
   code, checks the rule's optional condition, and creates one **`Task`** per
   matching rule.
3. The task closes either **by itself**, when the shipment fields it watches get
   filled, or **by a button**, when there is no field to watch.
4. Three other task kinds (weekly plan, local sell plan, truck allocation) are
   generated by their own code instead, and never touch `TaskRule` at all. Only
   one of the three is actually on a timer — see the table below.

## The four task kinds

`Task.kind` (`TaskKind`) says where a task came from. It decides which generator
owns it, which resolver closes it, and whether `Task.shipment` is set.

| Kind | Generated by | Trigger | `shipment` | Closes when |
|---|---|---|---|---|
| `shipment` | `generate_tasks_for_status()` (the rule engine) | shipment enters a status | set | its `completion_rule` is satisfied, or Mark Done |
| `weekly_plan` | `weekly_plan_tasks.py` | someone generates the week (the Weekly Plan page's action, or `run_weekly_plan_setup`) — **not on a timer** | null | that block's Mon–Sat plan cells are filled |
| `local_sell_plan` | `local_sell_plan_tasks.py` | a manager initializes a week (`generate_local_sell_plan_tasks` is the backstop) — **not on a timer** | null | every firm's row for the week is submitted, approved, or an all-zero draft |
| `truck_allocation` | `truck_allocation_tasks.py` | Celery beat, **Saturday 09:00** — the only one of the three on a timer | null | every day that needs a truck has a destination with ≥ 1 truck |

Only the first kind is rule-driven. The other three are code-driven, which is why
they do **not** appear in the rule catalog — their logic is in their own service
module and changing it needs a deploy.

**Some roles live entirely outside the rule table.** Rules exist only for
`sales_rep`, `document_team`, `transport`, `loading_dept_head`, `export_manager`
and `quality_inspector`. A `greenhouse_manager` has none: their whole queue is
`weekly_plan`. A `seller`'s is `local_sell_plan`. Any page or report that lists
"the tasks in the system" from `TaskRule` alone is therefore wrong for those two
roles — the Task Rules page carries the three kinds as their own table for exactly
this reason.

**And a task can outlive its rule.** Rules generate only on the transition *into*
a step, so a task created before a rule was reassigned or switched off keeps the
role it was given. That is why open tasks exist for `warehouse_chief` (146) and
`greenhouse_manager` (1) with no matching rule — the loading reassignment and the
quality-inspection rule's move off `greenhouse_manager`. Counts are as of
2026-09-22.

The three plan kinds resolve **lazily, from the task-read path**
(`MeTaskListView`), not from the save path. The person who fills a block's grid is
often not the manager the task is assigned to, and `greenhouse` may not import
`export` (see the dependency direction in `CLAUDE.md`), so there is no way to
close them from the write side.

## How a shipment task is born

`generate_tasks_for_status(shipment, new_status_code)` is called from
`transition_to()` in `services/shipment.py` — never from a Django signal (project
rule). For each active `TaskRule` with `step == new_status_code`:

1. **Condition check.** If the rule has a `condition_field`, the engine compares
   `str(getattr(shipment, condition_field)) == condition_value`. A blank
   `condition_field` always matches. Only one condition per rule — a rule needing
   two is written as two rules. This is how the gapy-satys split works: one rule
   for `is_gapy_satys=True` assigned to `document_team`, another for `False`
   assigned to `transport`.
2. **Idempotency.** A `(shipment, rule)` pair that already has a task is skipped,
   so re-running generation — or bouncing back into a status — never duplicates.
3. **Snapshot.** The new `Task` **copies** `target_fields`, `completion_rule`,
   `target_value` and `deadline_rule` off the rule. It does not read them back
   through the FK. See [Maintenance](#maintenance) — this is the single most
   surprising behaviour in the system.
4. **Deadline.** `deadline_rule` is parsed into an absolute `deadline` at creation
   time, anchored to the moment of the status change.

## Rule anatomy

One `TaskRule` row (`export_task_rule`):

| Column | Meaning |
|---|---|
| `step` | The shipment status **code** that opens this task (`draft`, `yuklenme`, …) |
| `title_key` | i18n key, e.g. `tasks.fill_loading_data` — the frontend resolves it in tk/ru/en |
| `assignee_role` | The role that owns the generated task |
| `target_fields` | **CSV** of shipment field keys — a `CharField`, not a JSONField (MSSQL rule). Read it with `Task.target_field_list`, never by hand |
| `completion_rule` | One of the four below |
| `target_value` | The comparison value, `FIELD_EQUALS` only |
| `deadline_rule` | Grammar below; blank means no deadline |
| `condition_field` / `condition_value` | The optional gate from step 1 above |
| `is_active` | A deactivated rule stops generating; tasks it already made survive |

### Completion rules

| `completion_rule` | Closes when |
|---|---|
| `all_fields_filled` | every field in `target_fields` is filled |
| `any_field_filled` | at least one is filled |
| `field_equals` | the field equals `target_value` (string-cast) |
| `manual_done` | never automatically — only the **Mark Done** button |

Auto-resolution runs in `Shipment.save()` (again, not a signal) via
`resolve_for_shipment()`, which re-checks every `open` / `in_progress` task on the
shipment.

**Mark Done tasks never gate the lifecycle.** `auto_advance_if_ready()` looks only
at the non-`MANUAL_DONE` tasks on a step, so *Give documents*, *Submit sales
report* and *Quality inspection* are reminders — a truck moves on without them.
That is deliberate: a field-based task on step 4 would freeze a truck at step 4
until the sales report arrives, which can be weeks.

### Deadline grammar

Parsed by `parse_deadline_rule()`; all times are Asia/Ashgabat.

| Rule | Means |
|---|---|
| `` (blank) or `none` | no deadline |
| `Nh_after_status` | N hours after the status change (any positive integer) |
| `HH:MM_same_day` | that time on the status-change date |
| `HH:MM_next_business_day` | that time on the next Mon–Fri (Fri → Mon) |
| `friday_eow` | the coming Friday 18:00 (today, if today is Friday) |

An unrecognised rule logs a warning and yields no deadline — a bad string never
crashes task generation.

## Task lifecycle

`Task.state` (`TaskState`): `open` → `in_progress` → `done`, with `blocked` and
`cancelled` off to the side.

- `in_progress` is set either by the **Start** action or automatically by
  `mark_started_for_changed_fields()` when someone edits a field the task watches.
- `blocked` carries a `blocked_reason` and an optional `blocked_by` set of other
  tasks.
- `cancelled` is admin/director only.
- `completed_by` credits the user who finished it — this, not `assignee_user`, is
  what the [[../screens/team-kpi]] leaderboard and `/me/kpi-today/` count.
- `is_overdue` is derived from `deadline` and is false for `done` / `cancelled`.

## Who sees it, who can act

The assigned role acts on its own tasks. **Supervisors** — `export_manager`,
`boss`, `admin`, `director` — can act on any task (`IsTaskActor`).

`Task.assignee_role` holds **one** role, but some roles are operationally the same
team. `task_roles_for(role)` in `apps/core/roles.py` is the single source of truth
for that expansion (currently `loading_dept_head` ↔ `loading_dept_head_deputy`),
and three call sites must all use it or visibility and permission drift apart —
someone would see a card they cannot touch. The full list is in [[task-rules]].

## Maintenance

**Each `Task` snapshots its rule's fields at creation.** Editing a `TaskRule`'s
`target_fields` or `completion_rule` leaves every existing open task on the old
values, so they will not auto-close. After changing rules:

```
python manage.py reconcile_tasks --dry-run   # preview
python manage.py reconcile_tasks             # apply + re-resolve
```

Other commands: `seed_task_rules` (seeds/updates the catalog), `backfill_tasks`
and `backfill_sales_report_tasks` (generate tasks for shipments that predate a
rule — rules only fire on transition **into** a step, so older shipments never get
one), `generate_local_sell_plan_tasks` (the cron backstop),
`resolve_weekly_plan_tasks`.

## Known limits

- **Reverse-FK targets.** A rule targeting `firm_splits` or `block_sources` relies
  on `Shipment.save()` running *after* the related rows are added. Adding a
  `ShipmentFirmSplit` does not save the parent, so such a task closes on the next
  event that touches the shipment.
- **Bulk operations bypass resolution.** `bulk_update` / raw SQL skip
  `Shipment.save()`, so no task resolves. All current write paths go through
  `serializer.save()`.
- **`FIELD_EQUALS` is a literal `==`, not "at or past".** Point `target_value` at
  a terminal enum state, or operators walk past it and the task hangs open.
- **No admin editing yet.** `TaskRule` rows are changed by `seed_task_rules` or
  Django admin, and the new Task Rules page is read-only. Editing from the app
  needs the `reconcile_tasks` step wired into the save path first, or an edit
  would silently strand every open task. Creating and cancelling ad-hoc tasks is
  also still missing (F15 in `docs/FINDINGS_BACKLOG.md`).
